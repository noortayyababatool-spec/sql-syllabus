Day 15: What a warehouse is: OLTP vs OLAP

Mon 19 October 2026 · 10 queries · run on AdventureWorks2022 (OLTP) and AdventureWorksDW2022 (warehouse)

Goal: explain in your own words why a company keeps two copies of its data in two different shapes.

Read: Microsoft Learn "What is a data warehouse" and "OLTP vs OLAP" (Azure Architecture Center). Kimball Group summary pages "Business requirements" and "Dimensional modeling".

The core idea: an OLTP database such as AdventureWorks2022 is built for many small writes: one order, one customer update, fast and safe. It is normalised, so each fact is stored once, and a report needs many joins. A warehouse such as AdventureWorksDW2022 copies that data into a shape built for reading: fewer, wider tables, already joined and labelled, so an analyst or Power BI can sum revenue by region by month in one simple query over millions of rows.
Setup: AdventureWorksDW2022 was restored from Microsoft's official sample backup (AdventureWorksDW2022.bak, sql-server-samples on GitHub) onto the same SQL Server Express instance, so both databases can be queried side by side.

Drill: see the difference

#1

1. Count the tables in each database

SELECT 'OLTP' AS Db, COUNT(*) AS Tables FROM AdventureWorks2022.INFORMATION_SCHEMA.TABLES WHERE TABLE_TYPE = 'BASE TABLE'
UNION ALL
SELECT 'DW', COUNT(*) FROM AdventureWorksDW2022.INFORMATION_SCHEMA.TABLES WHERE TABLE_TYPE = 'BASE TABLE';

What this query does

INFORMATION_SCHEMA.TABLES lists every table and view in a database; TABLE_TYPE = 'BASE TABLE' keeps the real tables. Putting the database name in front (AdventureWorks2022.INFORMATION_SCHEMA...) lets one query look at two databases, and UNION ALL stacks the two counts. The OLTP database has 72 tables, the warehouse 31.

📍 Fewer tables is the point of a warehouse: the OLTP design splits data into many small tables so each fact is stored once; the warehouse merges them back into a few wide ones.

#2

2. List the warehouse tables: Dim and Fact

SELECT TABLE_NAME FROM AdventureWorksDW2022.INFORMATION_SCHEMA.TABLES WHERE TABLE_TYPE = 'BASE TABLE' ORDER BY TABLE_NAME;

What this query does

Sorting by name groups the warehouse tables by prefix. 16 start with Dim (dimensions: the who, what, where and when, such as DimCustomer, DimProduct, DimDate) and 10 start with Fact (events and measurements, such as FactInternetSales and FactResellerSales). The other 5 are housekeeping (AdventureWorksDWBuildVersion, DatabaseLog, sysdiagrams) or staging-style tables (NewFactCurrencyRate, ProspectiveBuyer). The screenshot shows the first rows; the full list is 31.

📍 The naming is a promise: any Fact table holds numbers you add up and keys ending in Key; any Dim table holds text you filter and group by.

#3

3. Same question, OLTP: revenue by territory and year

USE AdventureWorks2022;
SELECT t.Name AS Territory, YEAR(h.OrderDate) AS Yr, SUM(h.TotalDue) AS Revenue
FROM Sales.SalesOrderHeader h
JOIN Sales.SalesTerritory t ON h.TerritoryID = t.TerritoryID
GROUP BY t.Name, YEAR(h.OrderDate) ORDER BY Territory, Yr;

What this query does

In the OLTP database the year is not stored anywhere: YEAR(h.OrderDate) computes it for every one of the 31,465 orders, and the GROUP BY must repeat the same expression. The territory name lives in a separate table in the same Sales schema, so one join is needed. 10 territories x 4 years (2011 to 2014) = 40 rows. This sums TotalDue, which includes tax and freight, for every order: online and reseller.

📍 Wrapping a column in a function, like YEAR(OrderDate), also stops SQL Server from seeking an index on that column (Day 12). The warehouse avoids this by storing the year as its own column.

#4

3. Same question, warehouse: revenue by territory and year

USE AdventureWorksDW2022;
SELECT st.SalesTerritoryRegion AS Territory, d.CalendarYear AS Yr, SUM(f.SalesAmount) AS Revenue
FROM dbo.FactInternetSales f
JOIN dbo.DimSalesTerritory st ON f.SalesTerritoryKey = st.SalesTerritoryKey
JOIN dbo.DimDate d ON f.OrderDateKey = d.DateKey
GROUP BY st.SalesTerritoryRegion, d.CalendarYear ORDER BY Territory, Yr;

What this query does

The warehouse answers the same shape of question with two simple joins: the fact table holds the numbers (SalesAmount) and two integer keys; DimSalesTerritory supplies the name and DimDate supplies CalendarYear as a ready-made column, so there is no function to compute. It returns 41 rows. The numbers do not match the OLTP query, and the next step shows why.

📍 Same question, different answer. Before trusting any report, check what the source table contains: FactInternetSales holds online orders only, and SalesAmount excludes tax and freight.

#5

Why the two answers differ: reconcile the totals

SELECT 'OLTP: every order, TotalDue' AS Source, SUM(TotalDue) AS Revenue, MIN(OrderDate) AS FirstOrder, MAX(OrderDate) AS LastOrder
FROM AdventureWorks2022.Sales.SalesOrderHeader
UNION ALL
SELECT 'OLTP: online orders only, SubTotal', SUM(SubTotal), MIN(OrderDate), MAX(OrderDate)
FROM AdventureWorks2022.Sales.SalesOrderHeader WHERE OnlineOrderFlag = 1
UNION ALL
SELECT 'DW: FactInternetSales, SalesAmount', SUM(SalesAmount), MIN(OrderDate), MAX(OrderDate)
FROM AdventureWorksDW2022.dbo.FactInternetSales;

What this query does

An extra check, not in the drill. Row 1 is what the OLTP query summed: 123.2 million, every order including reseller orders, tax and freight. Row 2 restricts the OLTP data to online orders (OnlineOrderFlag = 1) and uses SubTotal, which excludes tax and freight: 29,358,677.2207. Row 3, the warehouse fact table, gives exactly the same total to four decimal places. So the warehouse holds the same online orders, but its order dates run from 29 December 2010 to 28 January 2014 instead of 31 May 2011 to 30 June 2014: the sample's dates were shifted about five months earlier, which is why the per-year figures differ.

📍 A warehouse is a copy, so it must reconcile with its source. Matching the grand total exactly (and finding the date shift) is the kind of check a data engineer runs after every load.

#6

4. Customer with geography, OLTP: count the joins

USE AdventureWorks2022;
SELECT TOP 5 p.FirstName, p.LastName, a.City, sp.Name AS StateProvince, cr.Name AS Country
FROM Sales.Customer c
JOIN Person.Person p ON c.PersonID = p.BusinessEntityID
JOIN Person.BusinessEntityAddress bea ON p.BusinessEntityID = bea.BusinessEntityID
JOIN Person.Address a ON bea.AddressID = a.AddressID
JOIN Person.StateProvince sp ON a.StateProvinceID = sp.StateProvinceID
JOIN Person.CountryRegion cr ON sp.CountryRegionCode = cr.CountryRegionCode;

What this query does

Five joins across six tables in two schemas to print a name and where the person lives. Each step exists because the OLTP design stores every fact once: the name is on Person, the link to an address is in BusinessEntityAddress (a person can have several), the city on Address, the state on StateProvince, and the country on CountryRegion. Updating a country name means changing one row, which is what OLTP is built for.

📍 Normalised means each fact is stored in exactly one place. It makes writes safe and cheap, and makes reads long.

#7

4. Customer with geography, warehouse: one join

USE AdventureWorksDW2022;
SELECT TOP 5 c.FirstName, c.LastName, g.City, g.StateProvinceName, g.EnglishCountryRegionName
FROM dbo.DimCustomer c JOIN dbo.DimGeography g ON c.GeographyKey = g.GeographyKey;

What this query does

The warehouse already did those joins once, during the load: DimCustomer carries the person's name and a GeographyKey, and DimGeography holds city, state and country together in one flat row. One join gives the same columns, and here even the same five people (Jon Yang, Eugene Huang, Ruben Torres, Christy Zhu, Elizabeth Johnson). That match is luck: TOP 5 without ORDER BY returns whichever rows SQL Server reads first, and the same OLTP query run from a script connection returned five different customers. Add ORDER BY whenever the choice of rows matters.

📍 Denormalising means copying descriptive data into fewer, wider tables so readers do not have to join. The warehouse pays the join cost once at load time instead of every time someone asks.

#8

5. Column count of a product: OLTP vs warehouse

SELECT COUNT(*) AS OltpProductColumns FROM AdventureWorks2022.INFORMATION_SCHEMA.COLUMNS WHERE TABLE_NAME = 'Product';
SELECT COUNT(*) AS DwProductColumns FROM AdventureWorksDW2022.INFORMATION_SCHEMA.COLUMNS WHERE TABLE_NAME = 'DimProduct';

What this query does

INFORMATION_SCHEMA.COLUMNS has one row per column, so COUNT(*) gives the width of a table. The OLTP Production.Product has 25 columns; DimProduct has 36. (Column aliases were added so the two result grids are labelled.)

📍 Wider on purpose: DimProduct carries descriptions in eight languages, the model name, a photo and StartDate, EndDate and Status for price history, so a report never has to look anywhere else.

#9

5. What a wide dimension looks like

SELECT TOP 3 * FROM AdventureWorksDW2022.dbo.DimProduct;

What this query does

The first three products, all columns. ProductKey is the warehouse's own integer key, ProductAlternateKey (AR-5381) is the product number from the OLTP system, then names in English, Spanish and French, cost, colour, list price and so on. These first rows are parts such as Adjustable Race, so many attributes are NULL; bikes fill them in. The grid continues to the right with descriptions in more languages, a LargePhoto image and the history dates.

📍 Day 16 explains the two keys: ProductKey is a surrogate key the warehouse invents, ProductAlternateKey is the natural key from the source.

Self-test support

#10

Matching table pairs: OLTP to warehouse

SELECT 'Sales.SalesOrderDetail (online)' AS OltpTable, (SELECT COUNT(*) FROM AdventureWorks2022.Sales.SalesOrderDetail d
        JOIN AdventureWorks2022.Sales.SalesOrderHeader h ON h.SalesOrderID = d.SalesOrderID WHERE h.OnlineOrderFlag = 1) AS OltpRows,
       'FactInternetSales' AS DwTable, (SELECT COUNT(*) FROM AdventureWorksDW2022.dbo.FactInternetSales) AS DwRows
UNION ALL SELECT 'Production.Product', (SELECT COUNT(*) FROM AdventureWorks2022.Production.Product),
       'DimProduct', (SELECT COUNT(*) FROM AdventureWorksDW2022.dbo.DimProduct)
UNION ALL SELECT 'Sales.Customer (people)', (SELECT COUNT(*) FROM AdventureWorks2022.Sales.Customer WHERE PersonID IS NOT NULL AND StoreID IS NULL),
       'DimCustomer', (SELECT COUNT(*) FROM AdventureWorksDW2022.dbo.DimCustomer)
UNION ALL SELECT 'Sales.SalesTerritory', (SELECT COUNT(*) FROM AdventureWorks2022.Sales.SalesTerritory),
       'DimSalesTerritory', (SELECT COUNT(*) FROM AdventureWorksDW2022.dbo.DimSalesTerritory)
UNION ALL SELECT 'Sales.Store', (SELECT COUNT(*) FROM AdventureWorks2022.Sales.Store),
       'DimReseller', (SELECT COUNT(*) FROM AdventureWorksDW2022.dbo.DimReseller);

What this query does

An extra check for the self-test question 'which tables correspond'. Each row puts an OLTP table next to its warehouse version with both row counts. Online order lines: 60,398 in both. Individual customers (Sales.Customer rows that are a person, not a store): 18,484 in both. Stores and DimReseller: 701 in both. Products: 504 vs 606, because DimProduct keeps old versions of products whose price changed (Day 16). Territories: 10 vs 11, because the warehouse adds an 'NA' row for sales with no known territory.

📍 Equal row counts are a fast first test that a load copied everything. Where they differ, the difference should have a reason you can name.

Written exercise: OLTP vs OLAP

OLTP (online transaction processing)OLAP (online analytical processing)
PurposeRun the business: record each sale, payment and change the moment it happens, correctly.Understand the business: answer questions over history, such as which region grew and which product is falling.
Typical queryTouch a few rows by key: insert order 75124, update one customer's address, look up one order.Read and aggregate many rows: total revenue by territory by year over all 60,398 order lines.
Who uses itApplications: the website, the sales app, the warehouse scanner. Many users at once, each doing small things.Analysts, managers, finance, Power BI reports and dashboards. Fewer users, each asking big questions.
Write patternConstant small INSERT, UPDATE and DELETE statements all day, each in its own transaction.Loaded in batches by an ETL job (SSIS), for example every night; between loads it is read-only.
NormalisationHighly normalised: each fact stored once (a country name lives only in Person.CountryRegion), so an update changes one row.Denormalised on purpose: descriptions are copied into dimension rows (DimGeography holds city, state and country together), so reads need few joins.
Table shapeMany narrow tables linked by foreign keys: 72 tables in AdventureWorks2022.A few fact tables (tall, numeric) surrounded by dimensions (short, wide, text): 31 tables in AdventureWorksDW2022.
ExampleSales.SalesOrderHeader + Sales.SalesOrderDetail + Production.Product + Person.Person and its address chain.FactInternetSales joined to DimProduct, DimCustomer, DimDate and DimSalesTerritory.
What would go wrong if Power BI ran directly against the OLTP database all day?
Every visual would send a query with five or six joins and functions on date columns, scanning large tables, and these long reads would compete with the website and sales app for the same CPU, memory and disk. Reads also take shared locks, so a big report query can block, or be blocked by, the small writes that take orders, and checkout pages slow down. The report logic would be fragile too: every report would have to repeat the same joins and business rules (which orders count as revenue, tax or no tax), so two reports could disagree, as Drill 3 showed. And the OLTP database usually keeps only current values, so history such as last year's price is lost when a row is updated. A warehouse moves that load to a separate copy, does the joins once at load time, and keeps history.

Self-test: answers

Define OLTP and OLAP. OLTP is a database design for recording transactions as they happen: many small, fast, safe writes. OLAP is a design for analysing data: large reads that aggregate history, served from a warehouse built for reading.

Three differences. (1) Workload: small writes vs large reads. (2) Shape: normalised, many narrow tables vs denormalised facts and dimensions. (3) Freshness and history: current state, updated in place vs loaded in batches and keeping history (DimProduct keeps old price versions).

What normalised means and why the warehouse undoes it. Normalised means each fact is stored in exactly one place and other tables refer to it by key, so updates cannot leave copies out of step. The warehouse undoes it because it is not updated by users: it is loaded in batches, so repeated text costs little, and in return every report runs with one or two joins instead of six.

Table pairs. Sales.SalesOrderDetail (online orders) to FactInternetSales, 60,398 rows each. Production.Product to DimProduct (504 products, 606 rows with history). Sales.Customer (people) to DimCustomer, 18,484 each. Sales.Store to DimReseller, 701 each. Sales.SalesTerritory to DimSalesTerritory (10 + an NA row).
