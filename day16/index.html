Day 16: Fact tables vs dimension tables

Tue 20 October 2026 · 19 queries · run on AdventureWorksDW2022

Goal: look at any table and say which it is, what its grain is, and which columns are measures, keys and attributes.

Read: Kimball Group summary pages "Fact table structure", "Dimension table structure", "Grain" and "Additive, semi-additive, non-additive facts". Microsoft Learn "Understand star schema and the importance for Power BI", sections on fact and dimension tables.

TermMeaningAdventureWorksDW example
Fact tableRecords events or measurements. Many rows, narrow, mostly numbers and keysFactInternetSales, one row per order line
Dimension tableDescribes the who, what, where and when of a fact. Fewer rows, wide, mostly textDimProduct, DimCustomer, DimDate
GrainWhat one row in the fact table represents. Decide this first, alwaysOne row = one product on one order
MeasureA numeric column in a fact that you add upSalesAmount, OrderQuantity, TaxAmt
Surrogate keyAn integer key the warehouse invents, not the source system's IDProductKey (vs ProductAlternateKey, the OLTP ProductNumber)
Foreign key in a factPoints at one dimension rowProductKey, CustomerKey, OrderDateKey
AttributeA descriptive column in a dimension that you filter or group byEnglishProductName, Color, CalendarQuarter
Degenerate dimensionA dimension-like value stored directly in the fact because it has no attributes of its ownSalesOrderNumber in FactInternetSales
Additivity: SalesAmount is additive (sum across any dimension). Inventory on hand is semi-additive (sum across products, not across dates). Unit price is non-additive (never sum it; recompute it from additive parts). Say which type a measure is before you aggregate it.

Drill

#1

1. Anatomy of a fact table

USE AdventureWorksDW2022;
SELECT COLUMN_NAME, DATA_TYPE FROM INFORMATION_SCHEMA.COLUMNS WHERE TABLE_NAME = 'FactInternetSales' ORDER BY ORDINAL_POSITION;

What this query does

ORDER BY ORDINAL_POSITION lists the columns in the order they were created. The first eight all end in Key and are int: ProductKey, OrderDateKey, DueDateKey, ShipDateKey, CustomerKey, PromotionKey, CurrencyKey, SalesTerritoryKey. Each points at one dimension row. Then SalesOrderNumber and SalesOrderLineNumber identify the order line, and the rest are numbers: OrderQuantity (smallint), UnitPrice, ExtendedAmount, ProductStandardCost, TotalProductCost, SalesAmount, TaxAmt, Freight (all money). The only text columns are tracking and PO numbers. 26 columns; the screenshot shows the first 15.

📍 You can recognise a fact table from its column list alone: integer keys, money and quantity columns, almost no text.

#2

2. Anatomy of a dimension table

SELECT COLUMN_NAME, DATA_TYPE FROM INFORMATION_SCHEMA.COLUMNS WHERE TABLE_NAME = 'DimProduct' ORDER BY ORDINAL_POSITION;

What this query does

One key first (ProductKey, int), then mostly descriptive columns: ProductAlternateKey, names in English, Spanish and French, Color, Size, SizeRange, ProductLine, Class, Style, ModelName, and descriptions in eight languages (nvarchar). There are a few numbers (StandardCost, ListPrice, Weight) but they describe the product rather than record an event. The last three, StartDate, EndDate and Status, track history. 36 columns.

📍 A dimension is the list of words you can put in a report's slicer or row headers: colour, model, product line.

#3

3. Row counts: facts are tall, dimensions are short

SELECT 'FactInternetSales' AS T, COUNT(*) AS Rows FROM FactInternetSales
UNION ALL SELECT 'FactResellerSales', COUNT(*) FROM FactResellerSales
UNION ALL SELECT 'DimProduct', COUNT(*) FROM DimProduct
UNION ALL SELECT 'DimCustomer', COUNT(*) FROM DimCustomer
UNION ALL SELECT 'DimDate', COUNT(*) FROM DimDate
UNION ALL SELECT 'DimSalesTerritory', COUNT(*) FROM DimSalesTerritory;

What this query does

Six counts stacked with UNION ALL. The two fact tables have about 60,000 rows each (60,398 and 60,855). The dimensions are much smaller: 606 products, 11 territories and 3,652 dates (every day from 2005 to 2014, ten years). DimCustomer, at 18,484, is the exception: customer dimensions can be large, but they are still shorter than the facts that refer to them.

📍 Facts grow with every event; dimensions grow only when something new appears to describe. In a real warehouse the gap is millions to thousands.

#4

4. Prove the grain

SELECT SalesOrderNumber, SalesOrderLineNumber, COUNT(*)
FROM FactInternetSales
GROUP BY SalesOrderNumber, SalesOrderLineNumber
HAVING COUNT(*) > 1;

What this query does

The claimed grain is 'one row = one product on one order line'. If that is true, the pair (SalesOrderNumber, SalesOrderLineNumber) is unique, so grouping by it and keeping only groups with more than one row returns nothing. It returns 0 rows, so the grain holds for all 60,398 rows.

📍 State the grain first, then test it with exactly this GROUP BY ... HAVING COUNT(*) > 1 query. Duplicates at the grain are the most common way a fact load double-counts revenue.

#5

5. Surrogate key vs natural key

SELECT ProductKey, ProductAlternateKey, EnglishProductName
FROM DimProduct
WHERE EnglishProductName LIKE 'Mountain-100%';

What this query does

Each Mountain-100 bike has two identifiers. ProductKey (344 to 351) is a surrogate key: a plain integer the warehouse assigned. ProductAlternateKey (BK-M82S-38 and so on) is the natural key: the ProductNumber from Production.Product in the OLTP database. Fact tables join on ProductKey; the alternate key is kept so you can trace a row back to the source system.

📍 Surrogate keys are small, never change meaning, and belong to the warehouse. That last point matters in the next query.

#6

6. Why surrogate keys: one product, several rows

SELECT ProductAlternateKey, COUNT(*)
FROM DimProduct
GROUP BY ProductAlternateKey
HAVING COUNT(*) > 1;

What this query does

If ProductAlternateKey were unique this would return nothing. It returns 77 product numbers that appear more than once: 52 appear twice and 25 three times. Those are 179 rows for 77 products, so 102 rows are extra versions. 606 minus 102 is 504, exactly the number of products in the OLTP Production.Product table.

📍 The source system has one row per product; the warehouse keeps a new row each time a tracked attribute (here, the price) changes. The natural key cannot be the primary key any more, so the warehouse needs its own: the surrogate key. Day 20 covers this in full as a slowly changing dimension.

#7

6. One product's history

SELECT ProductKey, ProductAlternateKey, EnglishProductName, ListPrice, StartDate, EndDate, Status
FROM DimProduct
WHERE ProductAlternateKey = 'CA-1098';

What this query does

An extra look at one of the repeated products, the AWC Logo Cap. Three rows, three surrogate keys (223, 224, 225), one natural key. The list price was 8.6442 in the first two versions and 8.99 in the current one; Status = 'Current' and EndDate NULL mark the version in use now. A fact row points at whichever version was current when the sale happened; in this sample all 2,190 internet sales of the cap fall in the current version's period, so they all point at 225.

📍 Data quirk: the EndDate values (2007, 2008) are earlier than the StartDate values (2011, 2012). 200 of the 606 rows have this. The sample's dates were shifted when it was rebuilt, but not consistently; trust Status and NULL EndDate, not the date order.

#8

7. Every foreign key resolves: zero orphans

SELECT COUNT(*) AS Orphans
FROM FactInternetSales f
LEFT JOIN DimProduct p ON f.ProductKey = p.ProductKey
WHERE p.ProductKey IS NULL;

What this query does

The anti-join from Day 5: keep every fact row, attach the matching product, and count the rows where no product was found. The answer is 0, so every one of the 60,398 sales points at a real DimProduct row. If it were not 0, an INNER JOIN in a report would silently drop those sales.

📍 Run this check for every key in a fact table after every load. The 'NA' unknown member row seen in DimSalesTerritory exists so that facts with a missing value still have something to point at.

#9

8. An additive measure: the total

SELECT SUM(SalesAmount) AS Revenue FROM FactInternetSales;

What this query does

SalesAmount is additive: it can be summed across any dimension. The grand total is 29,358,677.2207, the same figure Day 15 reconciled against the OLTP online orders.

📍 Additive measures are the easy case and the most common: amounts, quantities, costs.

#10

8. Summed by product colour

SELECT p.Color, SUM(f.SalesAmount) AS Revenue
FROM FactInternetSales f
JOIN DimProduct p ON f.ProductKey = p.ProductKey
GROUP BY p.Color;

What this query does

The same measure grouped by an attribute from DimProduct. Eight colours; Black (8.84 million) and Red (7.72 million) sell the most. 'NA' is used for products with no colour, such as accessories. The eight figures add back up to the 29.36 million total.

📍 Grouping by a dimension attribute is the standard warehouse query: one fact, one join, one GROUP BY.

#11

8. Summed by calendar year

SELECT d.CalendarYear, SUM(f.SalesAmount) AS Revenue
FROM FactInternetSales f
JOIN DimDate d ON f.OrderDateKey = d.DateKey
GROUP BY d.CalendarYear;

What this query does

The same measure grouped by a DimDate attribute. Five years, 2010 to 2014; 2013 is the biggest at 16.35 million. 2010 and 2014 are tiny because the data covers only a few weeks of each (29 December 2010 to 28 January 2014). There is no ORDER BY, so the years come back in whatever order SQL Server finished grouping them; add ORDER BY d.CalendarYear for a report.

📍 By colour, by year, or in total, SUM(SalesAmount) is always right. That is what additive means.

#12

9. A non-additive measure: SUM(UnitPrice)

SELECT SUM(UnitPrice) AS SumUnitPrice FROM FactInternetSales;
SELECT SUM(SalesAmount) / SUM(OrderQuantity) AS WeightedAvgPrice FROM FactInternetSales;

What this query does

Adding up unit prices has no business meaning: it is not revenue, not a count, not a price. The correct way to get an average price is total revenue divided by total units: 486.0869. But look at the first number: 29,358,677.2207, exactly the revenue total. That is a coincidence of this table: every one of the 60,398 internet order lines has OrderQuantity = 1 and no discount, so price times 1 equals SalesAmount on every row.

📍 A wrong query can return a right-looking number. The next query uses the reseller table, where quantities vary, to show what SUM(UnitPrice) really does.

#13

9. The same test where quantities vary

SELECT SUM(UnitPrice) AS SumUnitPrice, SUM(SalesAmount) AS Revenue, SUM(OrderQuantity) AS Units,
       SUM(SalesAmount) / SUM(OrderQuantity) AS WeightedAvgPrice, AVG(UnitPrice) AS SimpleAvgPrice
FROM FactResellerSales;

What this query does

An extra check, not in the drill. Resellers buy many units per line (214,378 units on 60,855 lines). Here SUM(UnitPrice) is 27.0 million while real revenue is 80.5 million: the sum is simply wrong. Even AVG(UnitPrice), 444.43, is misleading because it gives a one-unit line the same weight as a 40-unit line. The weighted average, revenue divided by units, is 375.27.

📍 For a non-additive measure, never SUM and be careful with AVG: recompute it from additive parts (SUM of revenue / SUM of units).

#14

Semi-additive: inventory on hand

SELECT SUM(UnitsBalance) AS SumAcrossAllDates FROM FactProductInventory WHERE ProductKey = 1;
SELECT TOP 1 DateKey, UnitsBalance AS OnHandNow FROM FactProductInventory WHERE ProductKey = 1 ORDER BY DateKey DESC;

What this query does

An extra example for the third type. FactProductInventory stores a daily snapshot: one row per product per day with UnitsBalance, the stock on hand that day. Product 1 has 1,281 daily rows, each saying 875. Summing across dates gives 1,120,875 units, which never existed. The real answer is the balance on the last date: 875.

📍 Semi-additive: you may sum a balance across products (total stock today), but across dates you take the last value (or an average), never the sum.

#15

10. A fact table with a measure

SELECT TOP 10 * FROM FactSalesQuota;

What this query does

FactSalesQuota has 163 rows: one per salesperson per quarter, with one measure, SalesAmountQuota. EmployeeKey and DateKey point at dimensions; CalendarYear and CalendarQuarter are copied in for convenience. The quota is additive across salespeople (team quota) and across quarters within a year.

📍 Grain: one salesperson, one quarter, one target amount.

#16

10. A factless fact table

SELECT TOP 10 * FROM FactSurveyResponse;
SELECT COUNT(*) AS Responses FROM FactSurveyResponse;

What this query does

FactSurveyResponse has keys (DateKey, CustomerKey, ProductCategoryKey, ProductSubcategoryKey), two names copied in for convenience, and a date, but no numeric measure at all. One row means: on this date, this customer said in a survey that they had bought something from this product subcategory. Customer 11001 has three rows on 9 March 2012: Tights, Fenders and Hydration Packs.

📍 A factless fact records that an event happened. You measure it by counting rows: COUNT(*) responses per subcategory, per month, per customer.

Written exercise

#17

FactResellerSales: every foreign key and its dimension

SELECT c.name AS ForeignKeyColumn, OBJECT_NAME(fk.referenced_object_id) AS PointsAt
FROM sys.foreign_keys fk
JOIN sys.foreign_key_columns fc ON fc.constraint_object_id = fk.object_id
JOIN sys.columns c ON c.object_id = fc.parent_object_id AND c.column_id = fc.parent_column_id
WHERE fk.parent_object_id = OBJECT_ID('dbo.FactResellerSales')
ORDER BY c.name;

What this query does

Rather than guess from column names, this reads the foreign key constraints from the system catalog: sys.foreign_keys has one row per constraint, sys.foreign_key_columns says which column it is on, and OBJECT_NAME turns the referenced table's ID into a name. Nine keys: CurrencyKey to DimCurrency; OrderDateKey, DueDateKey and ShipDateKey all to DimDate; EmployeeKey to DimEmployee; ProductKey to DimProduct; PromotionKey to DimPromotion; ResellerKey to DimReseller; SalesTerritoryKey to DimSalesTerritory.

📍 DimDate appears three times: one dimension playing three roles (order, due and ship date). This is called a role-playing dimension.

#18

FactResellerSales: test the grain

SELECT SalesOrderNumber, SalesOrderLineNumber, COUNT(*)
FROM FactResellerSales
GROUP BY SalesOrderNumber, SalesOrderLineNumber
HAVING COUNT(*) > 1;

What this query does

Before writing the grain sentence for FactResellerSales, test it the same way as drill 4. Zero duplicates, so the grain is one row per product per reseller order line.

📍 Write the grain only after a query proves it.

#19

DimEmployee: which attributes are worth grouping by

SELECT COUNT(*) AS Employees, COUNT(DISTINCT DepartmentName) AS Departments, COUNT(DISTINCT Title) AS Titles,
       COUNT(DISTINCT SalesTerritoryKey) AS Territories, COUNT(DISTINCT Gender) AS Genders,
       COUNT(DISTINCT MaritalStatus) AS MaritalStatuses, COUNT(DISTINCT EmailAddress) AS Emails
FROM DimEmployee;

What this query does

COUNT(DISTINCT column) shows how many groups each attribute would produce. 296 rows. DepartmentName gives 16 groups, Title 67, SalesTerritoryKey 11, Gender 2, MaritalStatus 2: all useful row headers or slicers. EmailAddress has 290 distinct values for 296 rows, one group per person, so grouping by it just lists employees.

📍 A good grouping attribute has far fewer distinct values than the table has rows. Near-unique columns (email, phone, national ID) are for looking someone up, not for grouping.

Written exercise: DimEmployee

Five attributes to group by: DepartmentName (16 values), Title (67), SalesTerritoryKey via DimSalesTerritory (11), Gender (2), MaritalStatus (2). SalariedFlag and the year of HireDate also work.

One to never group by: EmailAddress. It has 290 distinct values in 296 rows, one per person, so grouping by it just lists employees one by one. The same is true of Phone, LoginID and EmployeeNationalIDAlternateKey, and EmployeePhoto is an image. (296 rows but 290 national IDs: like DimProduct, DimEmployee keeps history rows.)

Self-test: answers

Define grain. The grain is what one row of a fact table represents, stated in business terms, for example "one product on one internet sales order line". It is decided before anything else because it fixes which dimensions can attach and what a SUM means.

Two differences visible from INFORMATION_SCHEMA alone. (1) Data types: FactInternetSales is int keys plus money and smallint measures; DimProduct is mostly nvarchar text. (2) Keys: a fact has many columns ending in Key (eight foreign keys), a dimension has one key first and then attributes.

Why ProductKey and ProductAlternateKey both exist. ProductAlternateKey is the source system's product number, kept so a row can be traced back. ProductKey is the warehouse's surrogate key; it is needed because the warehouse keeps several versions of one product (77 product numbers appear 2 or 3 times), so the natural key is no longer unique, and because integer keys are small and fast to join.

One example of each. Additive: SalesAmount. Semi-additive: UnitsBalance in FactProductInventory (summing product 1 across dates gives 1,120,875, but there are only 875 on hand). Non-additive: UnitPrice.
