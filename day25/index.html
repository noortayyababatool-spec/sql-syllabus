Day 25: Data validation: checks, severities and a gate

Wed 18 November 2026 · 15 queries · run on AWPractice

Goal: test the loaded warehouse with recorded checks for completeness, uniqueness, validity, consistency and business rules, and decide automatically whether the load may be published.

Read: Microsoft Learn "EXCEPT and INTERSECT", "LEAD", "THROW"; Kimball Group "The 34 subsystems of ETL" (subsystem 4, data cleansing system, and the data quality screens).

Trust, but check: Day 24's load ran without an error, but "no error" only means SQL Server accepted the statements. It does not mean the numbers are right. Today ten checks test the warehouse the way an auditor would. Each check counts the rows that break one rule and writes the count to a results table. Checks have a severity: an Error stops the load from being published; a Warning lets it through and goes to a person. The checks found two real problems, and one of them leads back to a wrong assumption in Day 24.

Somewhere to record the results

#1

1. A run table and a results table

USE AWPractice;
DROP TABLE IF EXISTS etl.DQResult, etl.DQRun;
CREATE TABLE etl.DQRun (
    RunID     INT IDENTITY(1, 1) PRIMARY KEY,
    StartedAt DATETIME2(0) NOT NULL DEFAULT SYSDATETIME(),
    EndedAt   DATETIME2(0) NULL,
    Errors    INT NULL,
    Warnings  INT NULL);
CREATE TABLE etl.DQResult (
    ResultID   INT IDENTITY(1, 1) PRIMARY KEY,
    RunID      INT         NOT NULL REFERENCES etl.DQRun (RunID),
    CheckName  VARCHAR(60) NOT NULL,
    Category   VARCHAR(20) NOT NULL,
    Severity   VARCHAR(7)  NOT NULL CHECK (Severity IN ('Error', 'Warning')),
    FailedRows INT         NOT NULL,
    Status AS (CASE WHEN FailedRows = 0 THEN 'Pass' WHEN Severity = 'Error' THEN 'Fail' ELSE 'Warning' END),
    CheckedAt  DATETIME2(0) NOT NULL DEFAULT SYSDATETIME());
INSERT INTO etl.DQRun DEFAULT VALUES;     -- start run 1
SELECT RunID, StartedAt, EndedAt, Errors, Warnings FROM etl.DQRun;

What this query does

Two tables in the etl schema turn checks into data. etl.DQRun has one row per run of the checks, with the start and end times and the number of errors and warnings. etl.DQResult has one row per check per run: its name, its category, its severity and how many rows failed it. Status is a computed column: it is worked out from FailedRows and Severity every time it is read, so it can never disagree with them. A failed check with severity Error is 'Fail', one with severity Warning is 'Warning', and any check with no failed rows is 'Pass'. The CHECK constraint allows only the two severities. INSERT ... DEFAULT VALUES starts run 1, using the defaults for every column. Every check in this lesson has the same three parts: count the failing rows into @n, write one row to etl.DQResult, and show the evidence.

📍 A check that only prints a number is forgotten; a check that writes a row can be counted, compared and acted on.

Completeness and uniqueness

#2

2. Every order line reached the fact

DECLARE @run INT = (SELECT MAX(RunID) FROM etl.DQRun), @n INT;
DECLARE @stg INT = (SELECT COUNT(*) FROM stg.SalesOrderDetail), @fact INT = (SELECT COUNT(*) FROM dw.FactSales);
SET @n = ABS(@stg - @fact);
INSERT INTO etl.DQResult (RunID, CheckName, Category, Severity, FailedRows) VALUES (@run, 'Order lines: staging = fact', 'Completeness', 'Error', @n);
SELECT @stg AS StagingLines, @fact AS FactLines, @n AS Difference;

What this query does

The first and simplest check: the number of order lines in staging must equal the number in the fact table. Both are 121,319: the 121,317 AdventureWorks lines plus the two lines of Day 24's test order. Difference 0, so the check is recorded as passed. This is an Error-level check, because a missing or doubled row makes every total wrong. Notice that the check compares the warehouse with staging, not with AdventureWorks2022: staging holds the test order that the original source does not, and each check should compare two neighbouring steps of the pipeline, so a failure points at the step between them.

📍 Completeness: nothing was lost or doubled between staging and the warehouse.

#3

3. Every cent reached the fact

DECLARE @run INT = (SELECT MAX(RunID) FROM etl.DQRun), @n INT;
DECLARE @stg DECIMAL(19, 4) = (SELECT SUM(CAST(LineTotal AS DECIMAL(19, 4))) FROM stg.SalesOrderDetail),
        @fact DECIMAL(19, 4) = (SELECT SUM(SalesAmount) FROM dw.FactSales);
SET @n = CASE WHEN @stg = @fact THEN 0 ELSE 1 END;
INSERT INTO etl.DQResult (RunID, CheckName, Category, Severity, FailedRows) VALUES (@run, 'Revenue: staging = fact', 'Completeness', 'Error', @n);
SELECT @stg AS StagingRevenue, @fact AS FactRevenue, @fact - @stg AS Difference;

What this query does

The same comparison for money. Staging's LineTotal, rounded to 4 decimals with the same rule as the transform (Day 23), adds up to 109,847,916.4050, and so does the fact. Day 24's figure was 109,846,381.4250; the difference is the 1,534.98 test order. Comparing the rounded staging value is deliberate: comparing raw LineTotal would show the known 2.5-cent rounding difference every day, and a check that always fails is soon ignored. The accepted difference is built into the rule instead. FailedRows is 1 or 0 here, because a total is a single value that either matches or does not.

📍 Counting rows is not enough: a load can have every row and still the wrong amounts.

#4

4. Staging still matches the source, column by column

DECLARE @run INT = (SELECT MAX(RunID) FROM etl.DQRun), @n INT;
DECLARE @a INT = (SELECT COUNT(*) FROM (SELECT ProductID, Name, ProductNumber, Color, StandardCost, ListPrice, ProductSubcategoryID FROM dbo.Product
                                       EXCEPT
                                       SELECT ProductID, Name, ProductNumber, Color, StandardCost, ListPrice, ProductSubcategoryID FROM stg.Product) x),
        @b INT = (SELECT COUNT(*) FROM (SELECT ProductID, Name, ProductNumber, Color, StandardCost, ListPrice, ProductSubcategoryID FROM stg.Product
                                       EXCEPT
                                       SELECT ProductID, Name, ProductNumber, Color, StandardCost, ListPrice, ProductSubcategoryID FROM dbo.Product) x);
SET @n = @a + @b;
INSERT INTO etl.DQResult (RunID, CheckName, Category, Severity, FailedRows) VALUES (@run, 'Products: source = staging', 'Completeness', 'Error', @n);
SELECT (SELECT COUNT(*) FROM dbo.Product) AS SourceProducts, (SELECT COUNT(*) FROM stg.Product) AS StagingProducts,
       @a AS DifferentInSource, @b AS DifferentInStaging;

What this query does

EXCEPT returns the rows of the first query that are not in the second, comparing every listed column. Run in both directions, it finds products that differ in any column, exist only in the source or exist only in staging. Both counts are 0: the 509 products in staging (508 from Day 22 plus Practice Light) are exactly the 509 in dbo.Product. This check matters because of what a watermark cannot see. While preparing this lesson, a comparison of dbo.Product with the original AdventureWorks2022 found 116 products with different prices. 114 of them had been changed by earlier practice lessons (raised by 2, 5, 7 or 10 per cent) with an UPDATE that did not touch ModifiedDate, which still says 2014. An incremental extract based on ModifiedDate would never pick up such a change; a full compare does. Here they were already in the Day 22 full extract, so staging is correct.

📍 EXCEPT compares every column: it catches changes a ModifiedDate watermark cannot see.

#5

5. Keys are unique, and every product has exactly one current version

DECLARE @run INT = (SELECT MAX(RunID) FROM etl.DQRun), @n INT;
DECLARE @dupCust INT = (SELECT COUNT(*) FROM (SELECT CustomerID FROM dw.DimCustomer
                                              GROUP BY CustomerID HAVING COUNT(*) > 1) d),
        @badCurrent INT = (SELECT COUNT(*) FROM (SELECT ProductID FROM dw.DimProduct
                                                 GROUP BY ProductID HAVING SUM(CAST(IsCurrent AS INT)) <> 1) d),
        @dupFact INT = (SELECT COUNT(*) FROM (SELECT SalesOrderID, SalesOrderDetailID FROM dw.FactSales
                                              GROUP BY SalesOrderID, SalesOrderDetailID HAVING COUNT(*) > 1) d);
SET @n = @dupCust + @badCurrent + @dupFact;
INSERT INTO etl.DQResult (RunID, CheckName, Category, Severity, FailedRows) VALUES (@run, 'Keys unique; one current version', 'Uniqueness', 'Error', @n);
SELECT @dupCust AS DuplicateCustomers, @badCurrent AS ProductsWithout1CurrentVersion, @dupFact AS DuplicateFactLines;

What this query does

Three uniqueness rules in one check. No CustomerID appears twice in the Type 1 customer dimension. Every product has exactly one current version: not two, and not zero. No order line appears twice in the fact. All three are 0. The constraints from Day 24 already prevent two of these: the UNIQUE constraint on CustomerID and the fact's primary key. The filtered unique index on current products only prevents two current versions; it cannot prevent zero, which is what a failed Type 2 load without XACT_ABORT would leave behind. HAVING SUM(CAST(IsCurrent AS INT)) <> 1 catches both cases. A check costs almost nothing, so it is worth having even where a constraint exists: constraints get dropped to speed up a big load and are sometimes not put back.

📍 Constraints prevent some of these; a check also covers what no constraint can, such as zero current versions.

Validity and consistency

#6

6. Amounts add up on every line

DECLARE @run INT = (SELECT MAX(RunID) FROM etl.DQRun), @n INT;
SET @n = (SELECT COUNT(*) FROM dw.FactSales f
       JOIN stg.SalesOrderDetail d ON d.SalesOrderID = f.SalesOrderID AND d.SalesOrderDetailID = f.SalesOrderDetailID
       WHERE f.Quantity <= 0 OR f.UnitPrice < 0
          OR ABS(f.SalesAmount - f.Quantity * f.UnitPrice * (1 - d.UnitPriceDiscount)) > 0.01);
INSERT INTO etl.DQResult (RunID, CheckName, Category, Severity, FailedRows) VALUES (@run, 'Amount = quantity x price x (1 - discount)', 'Validity', 'Error', @n);
SELECT COUNT(*) AS LinesChecked, @n AS LinesFailed FROM dw.FactSales;

What this query does

Every fact line's SalesAmount is recomputed from its parts: quantity times unit price times one minus the discount, compared with a tolerance of 0.01 because the stored amount has been rounded. Negative prices and zero or negative quantities fail too. All 121,319 lines pass. The join back to staging is needed because the discount is not stored in the fact. If a transform rule were wrong (a discount applied twice, say), this check would fail on every discounted line, while the revenue reconciliation in step 3 would still pass, because staging and fact would agree with each other.

📍 Recompute a stored number from its parts: a wrong rule in the transform shows up here.

#7

7. Dates are in a possible order

DECLARE @run INT = (SELECT MAX(RunID) FROM etl.DQRun), @n INT;
SELECT @n = COUNT(*) FROM stg.SalesOrderHeader
WHERE OrderDate > SYSDATETIME() OR ShipDate < OrderDate OR DueDate < OrderDate;
INSERT INTO etl.DQResult (RunID, CheckName, Category, Severity, FailedRows) VALUES (@run, 'Order dates possible', 'Validity', 'Error', @n);
SELECT COUNT(*) AS Orders,
       SUM(CASE WHEN OrderDate > SYSDATETIME() THEN 1 ELSE 0 END) AS InTheFuture,
       SUM(CASE WHEN ShipDate < OrderDate THEN 1 ELSE 0 END)      AS ShippedBeforeOrdered,
       SUM(CASE WHEN DueDate  < OrderDate THEN 1 ELSE 0 END)      AS DueBeforeOrdered,
       SUM(CASE WHEN ShipDate IS NULL THEN 1 ELSE 0 END)          AS NotShippedYet
FROM stg.SalesOrderHeader;

What this query does

Dates must be possible: no order in the future, no order shipped or due before it was placed. All 31,466 orders pass. The column NotShippedYet shows 1: Day 24's test order, which is still being processed (status 1) and has no ship date. That is not an error, and the check deliberately allows it: ShipDate < OrderDate is unknown, not true, when ShipDate is NULL, so the row does not fail. Every validity rule has to decide which NULLs are allowed, and say so.

📍 A NULL ship date is not an error: an order can be open. Rules must say which NULLs are allowed.

#8

8. Type 2 history has no gaps and no overlaps

DECLARE @run INT = (SELECT MAX(RunID) FROM etl.DQRun), @n INT;
WITH v AS (
    SELECT ProductID, ValidFrom, ValidTo,
           LEAD(ValidFrom) OVER (PARTITION BY ProductID ORDER BY ValidFrom) AS NextFrom
    FROM dw.DimProduct)
SELECT @n = COUNT(*) FROM v
WHERE ValidFrom >= ValidTo                                  -- a version that ends before it starts
   OR (NextFrom IS NOT NULL AND NextFrom <> ValidTo)        -- a gap or an overlap before the next version
   OR (NextFrom IS NULL AND ValidTo <> '9999-12-31');       -- the last version is not open
INSERT INTO etl.DQResult (RunID, CheckName, Category, Severity, FailedRows) VALUES (@run, 'Product versions touch, no gaps', 'Consistency', 'Error', @n);
SELECT (SELECT COUNT(*) FROM dw.DimProduct) AS Versions,
       (SELECT COUNT(DISTINCT ProductID) FROM dw.DimProduct) AS Products, @n AS BadVersions;

What this query does

A Type 2 history is only usable if, for every product, any date falls into exactly one version. LEAD(ValidFrom) OVER (PARTITION BY ProductID ORDER BY ValidFrom) looks ahead to the next version of the same product. Three things count as failures: a version that ends before it starts; a next version that does not start exactly when this one ends (a gap leaves some sales with no product key, an overlap gives them two); and a last version that is not open until 9999-12-31. The 512 versions of 510 products (509 real products plus the Unknown member) all pass. Day 24's fact load relies on this rule silently; this check states it.

📍 LEAD looks at the next version of the same product: its start must be exactly this version's end.

#9

9. Facts still waiting on an Unknown member

DECLARE @run INT = (SELECT MAX(RunID) FROM etl.DQRun), @n INT;
SELECT @n = COUNT(*) FROM dw.FactSales WHERE CustomerKey = -1 OR ProductKey = -1;
INSERT INTO etl.DQResult (RunID, CheckName, Category, Severity, FailedRows) VALUES (@run, 'Facts on Unknown members', 'Consistency', 'Warning', @n);
SELECT SUM(CASE WHEN CustomerKey = -1 THEN 1 ELSE 0 END) AS UnknownCustomer,
       SUM(CASE WHEN ProductKey  = -1 THEN 1 ELSE 0 END) AS UnknownProduct
FROM dw.FactSales;

What this query does

Day 24 sent order 75124 to the Unknown customer until the customer arrived, then repaired it. This check counts fact rows still on an Unknown member: 0 customers and 0 products. Its severity is Warning, not Error, because Unknown is a legitimate temporary state: a late-arriving customer should not stop the whole load. But a warning that is there every day for the same rows means the repair step is not working, and the run table makes that visible over time.

📍 A Warning, not an Error: Unknown is allowed for a while, but it must be watched.

Business rules and plausibility

#10

10. A product that is "not for sale" was sold

DECLARE @run INT = (SELECT MAX(RunID) FROM etl.DQRun), @n INT;
SELECT @n = COUNT(DISTINCT p.ProductID)
FROM dw.FactSales f JOIN dw.DimProduct p ON p.ProductKey = f.ProductKey
WHERE p.Category = 'Not for sale';
INSERT INTO etl.DQResult (RunID, CheckName, Category, Severity, FailedRows) VALUES (@run, 'Sold products have a category', 'Business rule', 'Warning', @n);
SELECT p.ProductID, p.ProductName, p.Category, COUNT(*) AS Lines, SUM(f.SalesAmount) AS Revenue
FROM dw.FactSales f JOIN dw.DimProduct p ON p.ProductKey = f.ProductKey
WHERE p.Category = 'Not for sale'
GROUP BY p.ProductID, p.ProductName, p.Category;

What this query does

The first business rule check, and the first warning. Day 23's transform said that a product with no subcategory is 'Not for sale', because in AdventureWorks those are the components used to build bikes. Practice Light (1005), added on Day 22 without a subcategory, was sold on Day 24's test order: 1 line, 35.98. The data is not wrong in any technical way; an assumption in a rule is. The fix belongs to the data owner: either give the product a subcategory in the source, or change the label to something true, such as 'No category'. A warning is how the warehouse asks that question.

📍 A business rule check tests an assumption, here Day 23's "no subcategory means not for sale".

#11

11. Sold above its list price

DECLARE @run INT = (SELECT MAX(RunID) FROM etl.DQRun), @n INT;
SELECT @n = COUNT(*)
FROM dw.FactSales f JOIN dw.DimProduct p ON p.ProductKey = f.ProductKey
WHERE p.ProductKey > 0 AND f.UnitPrice > p.ListPrice;
INSERT INTO etl.DQResult (RunID, CheckName, Category, Severity, FailedRows) VALUES (@run, 'Unit price not above list price', 'Plausibility', 'Warning', @n);
SELECT p.ProductID, p.ProductName, p.ListPrice AS ListPriceInWarehouse,
       MIN(f.UnitPrice) AS LowestSold, MAX(f.UnitPrice) AS HighestSold, COUNT(*) AS Lines,
       MIN(f.OrderDateKey) AS FirstSale, MAX(f.OrderDateKey) AS LastSale
FROM dw.FactSales f JOIN dw.DimProduct p ON p.ProductKey = f.ProductKey
WHERE p.ProductKey > 0 AND f.UnitPrice > p.ListPrice
GROUP BY p.ProductID, p.ProductName, p.ListPrice;

What this query does

A plausibility check: a product sold above its list price is possible (a price can drop later) but unusual. One product fails, on 45 lines: Mountain-100 Black, 42 (ProductID 776). Its list price in the warehouse is 2,500.00, yet every sale, from 28 June 2011 to 28 May 2012, was at 3,374.99. Either the shop overcharged for a year, or the warehouse's price is wrong for that period. Warnings like this are why plausibility checks exist: no rule was broken, but something does not look right, and a person should look.

📍 Plausibility checks find data that is possible but suspicious, and send a person to look.

#12

12. Following the warning back to the source

SELECT 'AdventureWorks2022 Product' AS WhereFrom, ListPrice, ModifiedDate
FROM AdventureWorks2022.Production.Product WHERE ProductID = 776
UNION ALL
SELECT 'AdventureWorks2022 price history ' + CONVERT(CHAR(10), StartDate, 23) + ' to ' + CONVERT(CHAR(10), EndDate, 23),
       ListPrice, ModifiedDate
FROM AdventureWorks2022.Production.ProductListPriceHistory WHERE ProductID = 776
UNION ALL
SELECT 'AWPractice dbo.Product (our source)', ListPrice, ModifiedDate FROM dbo.Product WHERE ProductID = 776;

What this query does

The source of truth answers it. AdventureWorks2022 lists product 776 at 3,374.99, and its price history table says that price was valid from 31 May 2011 to 29 May 2012: every sale was at list price. Our source, AWPractice's dbo.Product, says 2,500.00, modified on 16 October 2026 by an earlier practice lesson. The warehouse is faithful to its source; the problem is a Day 24 assumption. The first version of every product was given ValidFrom 1900-01-01, which claims that today's price was also the price in 2011. That is true for most products and false for 776. Two honest fixes exist: start the first version on the day of the first load (and accept that older sales point to a version that did not exist yet), or build the first versions from the source's own price history, as AdventureWorks2022.ProductListPriceHistory allows. The choice is a design decision for Day 27.

📍 A warning is the start of an investigation: the answer was a change made in an earlier lesson.

Using the results

#13

13. The run, in one table

SELECT CheckName, Category, Severity, FailedRows, Status
FROM etl.DQResult WHERE RunID = (SELECT MAX(RunID) FROM etl.DQRun)
ORDER BY ResultID;

What this query does

The whole run as one table: ten checks, seven Errors and three Warnings by severity. All seven Error checks pass. Two Warnings are open: one product sold that is labelled 'Not for sale', and 45 lines sold above the warehouse's list price. This is the data quality report that goes to the people who own the data, and because each run is stored, the next run can be compared with this one: a warning that disappears was fixed; a new one is news.

📍 Ten checks, one row each: this table is the data quality report.

#14

14. Test the tests: plant an error and see it caught

DECLARE @failsPlanted INT, @diffPlanted DECIMAL(19, 4), @failsAfter INT, @diffAfter DECIMAL(19, 4);
BEGIN TRANSACTION;
UPDATE dw.FactSales SET SalesAmount = SalesAmount + 100            -- one wrong amount, on purpose
WHERE SalesOrderID = 43659 AND SalesOrderDetailID = 1;
SET @failsPlanted = (SELECT COUNT(*) FROM dw.FactSales f
       JOIN stg.SalesOrderDetail d ON d.SalesOrderID = f.SalesOrderID AND d.SalesOrderDetailID = f.SalesOrderDetailID
       WHERE f.Quantity <= 0 OR f.UnitPrice < 0
          OR ABS(f.SalesAmount - f.Quantity * f.UnitPrice * (1 - d.UnitPriceDiscount)) > 0.01);
SET @diffPlanted = (SELECT SUM(SalesAmount) FROM dw.FactSales)
       - (SELECT SUM(CAST(LineTotal AS DECIMAL(19, 4))) FROM stg.SalesOrderDetail);
ROLLBACK;                                                           -- undo it
SET @failsAfter = (SELECT COUNT(*) FROM dw.FactSales f
       JOIN stg.SalesOrderDetail d ON d.SalesOrderID = f.SalesOrderID AND d.SalesOrderDetailID = f.SalesOrderDetailID
       WHERE f.Quantity <= 0 OR f.UnitPrice < 0
          OR ABS(f.SalesAmount - f.Quantity * f.UnitPrice * (1 - d.UnitPriceDiscount)) > 0.01);
SET @diffAfter = (SELECT SUM(SalesAmount) FROM dw.FactSales)
       - (SELECT SUM(CAST(LineTotal AS DECIMAL(19, 4))) FROM stg.SalesOrderDetail);
SELECT 'One error planted' AS State, @failsPlanted AS AmountCheckFails, @diffPlanted AS RevenueDifference
UNION ALL
SELECT 'After ROLLBACK', @failsAfter, @diffAfter;

What this query does

A check that has never failed has never been tested: it might be unable to fail. Inside a transaction, one fact line (order 43659, line 1) is given 100 more than it should have. The amount check now finds 1 failing line, and the revenue comparison shows a difference of exactly 100.0000, so both checks catch it. ROLLBACK undoes the change, and the same two checks return 0 and 0.0000. The results are held in variables, because a variable keeps its value after a ROLLBACK, while the data changes are undone. Planting errors on purpose like this is the testing practice for data pipelines.

📍 A check that has never failed has never been tested. Break the data on purpose, inside a transaction.

#15

15. The gate: may this load be published?

DECLARE @run INT = (SELECT MAX(RunID) FROM etl.DQRun);
DECLARE @errors INT   = (SELECT COUNT(*) FROM etl.DQResult WHERE RunID = @run AND Status = 'Fail'),
        @warnings INT = (SELECT COUNT(*) FROM etl.DQResult WHERE RunID = @run AND Status = 'Warning');
UPDATE etl.DQRun SET EndedAt = SYSDATETIME(), Errors = @errors, Warnings = @warnings WHERE RunID = @run;
IF @errors > 0
    THROW 50001, 'Data quality errors found: the load must not be published.', 1;
PRINT CONCAT('Run ', @run, ': ', @errors, ' errors, ', @warnings, ' warnings.');
PRINT 'The load can be published. The warnings go to the data owner to investigate.';

What this query does

The gate turns the results into a decision. It counts the failed Error checks (0) and the open warnings (2) for the run, stores them in etl.DQRun with the end time, and then decides: if there were any errors, THROW stops with error 50001 and the message that the load must not be published. A scheduler (SQL Server Agent, SSIS or Azure Data Factory) sees the failure and does not continue, so a wrong number never reaches a report. Here there are none, so the two PRINT lines appear on the Messages tab: run 1 has 0 errors and 2 warnings, and the load can be published while the warnings go to the data owner. On Day 26 this gate becomes the last step of the load procedure.

📍 Errors stop the load (THROW); warnings let it through and go to a person.

Self-test: answers

Error or Warning? Error when a report would be wrong and nobody could tell (lost rows, a total that does not match, a duplicate). Warning when the data might be right but needs a person (a late customer, an odd price, a broken assumption).

Why compare neighbouring steps (staging vs fact) and not the first and last? Because a failure then names the step that caused it. Staging vs fact also includes the test order that AdventureWorks2022 does not have, so a source-to-fact comparison would fail for a reason that is not a fault.

Why check what a constraint already prevents? Constraints are dropped for big loads and not always put back, and some rules have no constraint at all: a filtered unique index stops two current versions but not zero.

How do you know a check works? Make it fail on purpose. Step 14 adds 100 to one line inside a transaction; both checks catch it, and ROLLBACK puts the data back.

Why did the warehouse have the wrong price for product 776? Not because of a fault in the load: it copied its source faithfully. The first Type 2 version claimed to be valid since 1900, and for this product the price had been different in 2011. Checks find symptoms; the cause can be an assumption made days earlier.
