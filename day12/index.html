Day 12: Indexes and execution plans

Wed 14 October 2026 · 32 queries · run on AWPractice (a practice copy)

Goal: read an execution plan, know what an index does, and explain why a query is slow in one sentence.

Read: Microsoft Learn "Clustered and nonclustered indexes described" and "Display an actual execution plan". Brent Ozar, "How to think like the SQL Server engine" (first 30 minutes).

The sentence you need: a slow query is usually a scan where a seek was possible, caused by no index, a function wrapped around the column, a leading wildcard, or an implicit conversion. Check those four before anything else.
How to read the numbers: every screenshot shows the actual execution plan. The caption gives the logical reads from SET STATISTICS IO: each read is one 8 KB page, so fewer reads means less work.

Drill

#1

Setup: turn on reads and timings

USE AWPractice;
GO
-- Query menu > Include Actual Execution Plan (Ctrl+M) is switched on for the whole day
SET STATISTICS IO ON;
SET STATISTICS TIME ON;

What this query does

STATISTICS IO reports, for every table a query touches, how many 8 KB pages it read: 'logical reads'. That number is the best single measure of how much work a query did. STATISTICS TIME adds CPU and elapsed time. Include Actual Execution Plan (Ctrl+M) adds an Execution plan tab showing the steps SQL Server actually took. All three stay on for this query window.

#2

1. A lookup on a heap. Table Scan.

SELECT * FROM SalesOrderDetail WHERE SalesOrderID = 43659;

What this query does

SalesOrderDetail was copied with SELECT INTO, so it is a heap: rows stored in no particular order, with no index. To find order 43659 SQL Server has no choice but to read every page and check every row: a Table Scan, 1,494 logical reads (about 12 MB) for 12 rows. Read a plan from right to left; the arrow thickness shows how many rows flow between steps.

📍 No index means SQL Server must read every page of the table, 1,494 of them, to find 12 rows.

#3

2. Add a clustered index. Clustered Index Seek.

CREATE CLUSTERED INDEX CIX_SalesOrderDetail ON SalesOrderDetail (SalesOrderID, SalesOrderDetailID);

What this query does

Builds the index used in the next step. The plan shows how: SQL Server reads the whole table once, sorts the rows by the index key, and writes the sorted copy. That one-off cost is paid when the index is created, and a little more on every later INSERT, UPDATE and DELETE.

#4

2. Add a clustered index. Clustered Index Seek. (continued)

SELECT * FROM SalesOrderDetail WHERE SalesOrderID = 43659;

What this query does

A clustered index sorts the table itself by its key, here SalesOrderID then SalesOrderDetailID, and builds a tree above it, like the alphabetical order of a phone book. A table can have only one. Now SQL Server walks the tree straight to order 43659: a Clustered Index Seek, 3 logical reads instead of 1,494. Creating the index read the whole table once, which is a one-off cost.

📍 Same query, same 12 rows: 1,494 reads became 3. That is what an index is for.

#5

3. A lookup on a column with no index. Scan again.

SELECT * FROM SalesOrderDetail WHERE ProductID = 776;

What this query does

The clustered index is sorted by order number, not by product, so it does not help find ProductID 776. SQL Server reads the whole clustered index instead: a Clustered Index Scan, 1,513 reads. A scan of a clustered index is the same amount of work as a table scan; the name changes because the table is now stored inside the index.

#6

4. Nonclustered index on ProductID. Seek plus Key Lookup.

CREATE NONCLUSTERED INDEX IX_SalesOrderDetail_ProductID ON SalesOrderDetail (ProductID);

What this query does

Builds the index used in the next step. The plan shows how: SQL Server reads the whole table once, sorts the rows by the index key, and writes the sorted copy. That one-off cost is paid when the index is created, and a little more on every later INSERT, UPDATE and DELETE.

#7

4. Nonclustered index on ProductID. Seek plus Key Lookup. (continued)

SELECT * FROM SalesOrderDetail WHERE ProductID = 776;

What this query does

A nonclustered index is a separate, sorted copy of just its key column (ProductID) plus a pointer to the full row: the clustered key. The seek finds the 228 order lines for product 776 quickly, but SELECT * needs every column, so for each row SQL Server follows the pointer back into the clustered index: a Key Lookup, about 3 reads per row. Total 710 reads: better than 1,513, but the lookups are most of the cost. Hovering the Key Lookup icon shows its Output List, the columns it had to fetch.

📍 Key Lookup: the index found the rows, but SELECT * needs columns the index does not hold, so each of the 228 rows is fetched separately.

#8

5. Covering index. INCLUDE the columns you select.

SELECT ProductID, OrderQty, LineTotal FROM SalesOrderDetail WHERE ProductID = 776;

What this query does

Selecting only three columns does not help yet: OrderQty and LineTotal are still not in the ProductID index, so every row still needs a Key Lookup, and the reads stay at 710.

#9

5. Covering index. INCLUDE the columns you select. (continued)

CREATE NONCLUSTERED INDEX IX_SalesOrderDetail_ProductID_Covering ON SalesOrderDetail (ProductID) INCLUDE (OrderQty, LineTotal);

What this query does

Builds the index used in the next step. The plan shows how: SQL Server reads the whole table once, sorts the rows by the index key, and writes the sorted copy. That one-off cost is paid when the index is created, and a little more on every later INSERT, UPDATE and DELETE.

#10

5. Covering index. INCLUDE the columns you select. (continued)

SELECT ProductID, OrderQty, LineTotal FROM SalesOrderDetail WHERE ProductID = 776;

What this query does

INCLUDE stores extra columns in the bottom level of the index without sorting by them. Now the index holds everything this query asks for, so it 'covers' the query: one Index Seek, no lookups, 5 reads instead of 710. The trade-off is space and slower writes, because every INSERT, UPDATE or DELETE must now maintain one more copy of those columns (drill 9).

📍 710 reads became 5. A covering index holds every column the query needs.

#11

6. A function on the indexed column kills the seek

CREATE NONCLUSTERED INDEX IX_SalesOrderHeader_OrderDate ON SalesOrderHeader (OrderDate);

What this query does

Builds the index used in the next step. The plan shows how: SQL Server reads the whole table once, sorts the rows by the index key, and writes the sorted copy. That one-off cost is paid when the index is created, and a little more on every later INSERT, UPDATE and DELETE.

#12

6. A function on the indexed column kills the seek (continued)

SELECT COUNT(*) AS Orders2013 FROM SalesOrderHeader WHERE YEAR(OrderDate) = 2013;

What this query does

With YEAR() wrapped around OrderDate, SQL Server cannot use the sorted order of the index, because it would have to calculate YEAR() for every row to know which ones match. So it scans the entire OrderDate index: 88 reads. (It scans the small index rather than the 780-page table, because the index holds the only column the query needs.)

#13

6. A function on the indexed column kills the seek (continued)

SELECT COUNT(*) AS Orders2013 FROM SalesOrderHeader WHERE OrderDate >= '2013-01-01' AND OrderDate < '2014-01-01';

What this query does

Written as a date range on the bare column (the Day 2 habit), the condition matches the index order directly: SQL Server seeks to 1 January 2013 and reads until 1 January 2014. Index Seek, 41 reads instead of 88, the same 14,182 orders. The gap grows with table size: on a table with years of data, the function version reads everything and the range version reads one year.

📍 Same 14,182 orders, half the reads. Never wrap a filtered column in a function; rewrite the condition as a range.

#14

7. Leading wildcard kills the seek too

CREATE NONCLUSTERED INDEX IX_Product_Name ON Product (Name);

What this query does

Builds the index used in the next step. The plan shows how: SQL Server reads the whole table once, sorts the rows by the index key, and writes the sorted copy. That one-off cost is paid when the index is created, and a little more on every later INSERT, UPDATE and DELETE.

#15

7. Leading wildcard kills the seek too (continued)

SELECT Name FROM Product WHERE Name LIKE 'Mountain%';

What this query does

LIKE 'Mountain%' fixes the start of the text, and the index is sorted alphabetically, so SQL Server can seek straight to 'Mountain' and stop at the first name after it, like opening a dictionary at M: Index Seek, 3 reads.

#16

7. Leading wildcard kills the seek too (continued)

SELECT Name FROM Product WHERE Name LIKE '%Mountain%';

What this query does

With a wildcard at the start, the text could begin with anything, so the alphabetical order is no help and every name must be checked: Index Scan. Product is tiny (6 reads), but on a table with millions of rows this is the difference between instant and minutes. Searching inside text at scale needs full-text search, not LIKE '%...%'.

#17

8. See what indexes exist and how big they are

SELECT i.name, i.type_desc, OBJECT_NAME(i.object_id) AS TableName
FROM sys.indexes i WHERE OBJECT_NAME(i.object_id) IN ('SalesOrderDetail', 'SalesOrderHeader', 'Product');
EXEC sp_spaceused 'SalesOrderDetail';

What this query does

sys.indexes lists every index. A table with no clustered index shows a row of type HEAP (SalesOrderHeader is still a heap). sp_spaceused shows the space a table uses: index_size is the space taken by its nonclustered indexes, which here is a large fraction of the data size. Indexes are not free.

#18

9. Index write cost. Time an UPDATE with and without the indexes.

UPDATE SalesOrderDetail SET OrderQty = OrderQty WHERE ProductID = 776;
DROP INDEX IX_SalesOrderDetail_ProductID ON SalesOrderDetail;
DROP INDEX IX_SalesOrderDetail_ProductID_Covering ON SalesOrderDetail;
UPDATE SalesOrderDetail SET OrderQty = OrderQty WHERE ProductID = 776;

What this query does

Every index is a copy of some columns that must be kept in step with the table. With the two ProductID indexes in place, the UPDATE seeks its 228 rows quickly but must also write OrderQty into the covering index. After dropping them, finding the rows means scanning the table again. On a busy table, every extra index makes every INSERT, UPDATE and DELETE slower, so you index for the queries that matter, not for every column.

📍 Indexes speed up reads and slow down writes. The first UPDATE finds its rows fast; the second has to scan.

#19

10. Missing index hint

SELECT * FROM SalesOrderHeader WHERE CustomerID = 29825;

What this query does

SalesOrderHeader is a heap with no index on CustomerID, so 12 orders cost a 780-page Table Scan. The optimiser notices this and prints a green 'Missing Index' line at the top of the plan, with its estimated improvement and a CREATE INDEX statement (right-click > Missing Index Details). Treat it as a hint, not an order: it only considers this one query and never warns about write cost.

Stretch

#20

Compare against the real thing. AdventureWorks has proper indexes.

SELECT * FROM AdventureWorks2022.Sales.SalesOrderDetail WHERE ProductID = 776;

What this query does

AdventureWorks2022 was built with proper indexes, including a clustered primary key and a nonclustered index on ProductID, so the same query uses the drill 4 shape: Index Seek plus Key Lookup, about 710 reads. That is what drill 4 rebuilt by hand.

#21

Join plan shapes

SELECT h.SalesOrderID, d.ProductID FROM SalesOrderHeader h
JOIN SalesOrderDetail d ON h.SalesOrderID = d.SalesOrderID WHERE h.SalesOrderID = 43659;

What this query does

Nested Loops: for each row from one input, look up matching rows in the other. Best when one side is small, as here with a single order. The seek on SalesOrderDetail's clustered index makes each lookup cheap.

#22

Join plan shapes (continued)

SELECT h.SalesOrderID, d.ProductID FROM SalesOrderHeader h
JOIN SalesOrderDetail d ON h.SalesOrderID = d.SalesOrderID;

What this query does

Without a filter both sides are large and SalesOrderHeader is an unsorted heap, so SQL Server builds a hash table from one input in memory and probes it with the other: Hash Match, the workhorse for big unsorted joins. A Merge Join appears when both inputs arrive already sorted on the join key, for example when both tables have clustered indexes on SalesOrderID.

#23

Statistics and fragmentation

UPDATE STATISTICS SalesOrderDetail;
SELECT OBJECT_NAME(object_id) AS TableName, index_id, avg_fragmentation_in_percent
FROM sys.dm_db_index_physical_stats(DB_ID(), NULL, NULL, NULL, 'LIMITED') WHERE index_id > 0;

What this query does

Statistics are SQL Server's summary of how values are distributed in a column; the optimiser uses them to estimate how many rows each step returns. When the estimated and actual row counts in a plan are far apart, stale statistics are a common cause, and UPDATE STATISTICS refreshes them. sys.dm_db_index_physical_stats reports fragmentation: how out of order an index's pages are after many changes. Freshly built indexes, like today's, are close to 0%.

#24

What is running right now

SELECT session_id, status, command, cpu_time, total_elapsed_time, text
FROM sys.dm_exec_requests CROSS APPLY sys.dm_exec_sql_text(sql_handle) WHERE session_id > 50;

What this query does

sys.dm_exec_requests lists every request running on the server at this moment; CROSS APPLY sys.dm_exec_sql_text shows the SQL text of each. Session IDs above 50 are user sessions. On a quiet practice server the only row is this query itself; at work, this is the first query to run when 'the database is slow'.

Q2. SalesPersonID and OrderDate: make it seek, prove it with reads

SELECT SalesOrderID, OrderDate, TotalDue FROM SalesOrderHeader
WHERE SalesPersonID = 277 AND OrderDate >= '2013-01-01' AND OrderDate < '2014-01-01';

What this query does

Q2. SalesPersonID and OrderDate: make it seek, prove it with reads (continued)

CREATE NONCLUSTERED INDEX IX_SalesOrderHeader_SalesPerson_OrderDate
    ON SalesOrderHeader (SalesPersonID, OrderDate) INCLUDE (SalesOrderID, TotalDue);

What this query does

Builds the index used in the next step. The plan shows how: SQL Server reads the whole table once, sorts the rows by the index key, and writes the sorted copy. That one-off cost is paid when the index is created, and a little more on every later INSERT, UPDATE and DELETE.

#27

Q2. SalesPersonID and OrderDate: make it seek, prove it with reads (continued)

SELECT SalesOrderID, OrderDate, TotalDue FROM SalesOrderHeader
WHERE SalesPersonID = 277 AND OrderDate >= '2013-01-01' AND OrderDate < '2014-01-01';

What this query does

Key order matters: the column tested with = goes first, the range column second, so all of salesperson 277's 2013 orders sit next to each other in the index. On this heap, SalesOrderID also has to be INCLUDEd: a nonclustered index on a heap points to rows by a physical address, not by SalesOrderID, so without it every row would need a lookup, and in testing SQL Server ignored that version and kept scanning 780 pages. With it the index covers the query: Index Seek, 4 reads instead of 780.

📍 Equality column first, range column second. And on a heap, SalesOrderID must be INCLUDEd too.

#29

Q3. A Day 6 query that benefits from an index (continued)

SELECT TOP 5 CustomerID, SUM(TotalDue) AS Revenue
FROM SalesOrderHeader GROUP BY CustomerID ORDER BY Revenue DESC;

What this query does

Day 6's revenue-per-customer query needs only CustomerID and TotalDue. An index on CustomerID that INCLUDEs TotalDue holds just those two columns, already sorted by customer, so SQL Server reads that narrow index (about 104 pages) instead of the 780-page table, and can aggregate in order without a separate sort. The same index also fixes drill 10's missing-index warning: the lookup for customer 29825 becomes a seek.

#30

Q4. Rewrite LEFT(Name, 5) = 'Mount' so it can use the Name index

SELECT Name FROM Product WHERE LEFT(Name, 5) = 'Mount';

What this query does

LEFT() wraps the column, the same problem as YEAR() in drill 6: SQL Server cannot seek, so it scans the Name index.

#31

Q4. Rewrite LEFT(Name, 5) = 'Mount' so it can use the Name index (continued)

SELECT Name FROM Product WHERE Name LIKE 'Mount%';

What this query does

'Starts with Mount' written as LIKE 'Mount%' leaves the column bare and fixes the start of the text, so it seeks on IX_Product_Name: the same 38 products with half the reads. This is the third of the four slow-query causes: a function around the column.

#32

Q5. Drop every index created today and confirm with sys.indexes

DROP INDEX IF EXISTS CIX_SalesOrderDetail ON SalesOrderDetail;
DROP INDEX IF EXISTS IX_SalesOrderHeader_OrderDate ON SalesOrderHeader;
DROP INDEX IF EXISTS IX_SalesOrderHeader_SalesPerson_OrderDate ON SalesOrderHeader;
DROP INDEX IF EXISTS IX_SalesOrderHeader_CustomerID ON SalesOrderHeader;
DROP INDEX IF EXISTS IX_Product_Name ON Product;
SELECT OBJECT_NAME(object_id) AS TableName, name, type_desc FROM sys.indexes
WHERE OBJECT_NAME(object_id) IN ('SalesOrderDetail', 'SalesOrderHeader', 'Product');

What this query does

DROP INDEX IF EXISTS removes each index without failing if one is already gone (drill 9 dropped two). Afterwards sys.indexes shows SalesOrderDetail and SalesOrderHeader back to HEAP, and Product keeps only PK_Product, the primary key from Day 10, which was not created today.

Self-test Q1: one line each

Clustered index: the table itself, stored sorted by the index key; one per table. Nonclustered index: a separate sorted copy of a few columns with a pointer back to the full row; many per table. Covering index: a nonclustered index that holds every column a query needs (key plus INCLUDE), so no lookups back to the table.
Today in numbers: heap scan 1,494 reads → clustered seek 3 · ProductID seek with key lookups 710 → covering seek 5 · YEAR() scan 88 → date range seek 41 · SalesPersonID scan 780 → covering seek 4.
