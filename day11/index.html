Drill

#1

1. Variables

USE AWPractice;
GO
DECLARE @Territory INT = 1, @Year INT = 2013;
SELECT COUNT(*) AS Orders FROM SalesOrderHeader WHERE TerritoryID = @Territory AND YEAR(OrderDate) = @Year;

What this query does

DECLARE creates a variable (its name starts with @), gives it a data type and optionally a starting value. The variable can then be used anywhere a literal value could go. Changing @Territory or @Year re-runs the same query for a different territory or year without editing the WHERE clause. Variables only live until the end of the batch.

#2

2. Assign from a query, then use it

DECLARE @AvgPrice MONEY;
SELECT @AvgPrice = AVG(ListPrice) FROM Product WHERE ListPrice > 0;
SELECT Name, ListPrice FROM Product WHERE ListPrice > @AvgPrice * 2;
PRINT 'Average price is ' + CAST(@AvgPrice AS VARCHAR(20));

What this query does

SELECT @var = expression stores a query result in a variable instead of returning it. Here the average price is calculated once and reused: the next SELECT lists products costing more than twice that. PRINT writes text to the Messages tab, and CAST is needed because a number cannot be joined to text with +. Remember that AWPractice prices were raised on Day 9, so they differ from AdventureWorks.

#3

3. IF / ELSE

DECLARE @Count INT = (SELECT COUNT(*) FROM Product WHERE Color IS NULL);
IF @Count > 0 PRINT 'Products with no colour: ' + CAST(@Count AS VARCHAR(10));
ELSE PRINT 'All products have a colour';

What this query does

IF runs the next statement only when its condition is true; ELSE runs when it is false. A subquery in brackets can set a variable directly. On Day 9 the NULL colours were changed to Black and committed, so only the 4 practice products added later have no colour, and the IF branch prints that count.

#4

4. WHILE. Rarely the right tool in SQL, but you need to read it.

DECLARE @i INT = 1;
WHILE @i <= 5
BEGIN
    PRINT 'Iteration ' + CAST(@i AS VARCHAR(2));
    SET @i = @i + 1;
END;

What this query does

WHILE repeats a block as long as its condition is true; BEGIN ... END groups several statements into one block. SET changes a variable's value. Forgetting to increase @i makes an endless loop. SQL is built to work on whole sets of rows at once, so loops are usually slower than one set-based statement; they are for admin scripts, not for processing data row by row.

#5

5. Your first stored procedure

CREATE OR ALTER PROCEDURE dbo.usp_GetTerritoryOrders
    @TerritoryID INT,
    @Year INT
AS
BEGIN
    SET NOCOUNT ON;
    SELECT SalesOrderID, OrderDate, TotalDue
    FROM SalesOrderHeader
    WHERE TerritoryID = @TerritoryID AND YEAR(OrderDate) = @Year
    ORDER BY OrderDate;
END;
GO
EXEC dbo.usp_GetTerritoryOrders @TerritoryID = 1, @Year = 2013;
EXEC dbo.usp_GetTerritoryOrders 4, 2014;

What this query does

A stored procedure is a saved, named batch of SQL with parameters. CREATE OR ALTER makes it re-runnable (Day 10). SET NOCOUNT ON stops the '(n rows affected)' messages, which can confuse programs like SSIS that call the procedure. EXEC runs it: parameters can be passed by name (@TerritoryID = 1), which is clearer and order-independent, or by position (4, 2014). Each call returns its own result set.

#6

6. Default parameter and an OUTPUT parameter

CREATE OR ALTER PROCEDURE dbo.usp_TerritoryRevenue
    @TerritoryID INT,
    @Year INT = NULL,
    @Revenue DECIMAL(18,2) OUTPUT
AS
BEGIN
    SET NOCOUNT ON;
    SELECT @Revenue = SUM(TotalDue)
    FROM SalesOrderHeader
    WHERE TerritoryID = @TerritoryID AND (@Year IS NULL OR YEAR(OrderDate) = @Year);
END;
GO
DECLARE @R DECIMAL(18,2);
EXEC dbo.usp_TerritoryRevenue @TerritoryID = 1, @Revenue = @R OUTPUT;
SELECT @R AS AllYears;
EXEC dbo.usp_TerritoryRevenue @TerritoryID = 1, @Year = 2013, @Revenue = @R OUTPUT;
SELECT @R AS Only2013;

What this query does

@Year = NULL is a default: callers can leave it out. The WHERE pattern (@Year IS NULL OR YEAR(OrderDate) = @Year) means 'no year given, so every year'. An OUTPUT parameter sends a value back to the caller instead of a result set: the caller passes a variable marked OUTPUT and reads it afterwards. OUTPUT is needed in both the procedure definition and the EXEC, or the value is silently not returned.

#7

7. The load procedure. SSIS will call this on Day 13.

CREATE OR ALTER PROCEDURE reporting.usp_LoadSalesSummary
AS
BEGIN
    SET NOCOUNT ON;
    TRUNCATE TABLE reporting.SalesSummary;
    INSERT INTO reporting.SalesSummary (TerritoryID, YearMonth, OrderCount, Revenue)
    SELECT TerritoryID, FORMAT(OrderDate, 'yyyy-MM'), COUNT(*), SUM(TotalDue)
    FROM SalesOrderHeader GROUP BY TerritoryID, FORMAT(OrderDate, 'yyyy-MM');
    SELECT @@ROWCOUNT AS RowsLoaded;
END;
GO
EXEC reporting.usp_LoadSalesSummary;

What this query does

The Day 10 re-runnable load, packaged so it can be called by name, scheduled, or called from SSIS. TRUNCATE empties the table first; the INSERT reloads it; @@ROWCOUNT, read straight after the INSERT, reports how many rows went in: 364, the same every time it runs. TRUNCATE works here because SalesSummary is the child in its foreign key; a table referenced by a foreign key cannot be truncated.

📍 The Day 10 lesson, packaged: truncate then insert, so the load can be run any number of times.

#8

8. Scalar function

CREATE OR ALTER FUNCTION dbo.fn_PriceBand (@Price MONEY)
RETURNS VARCHAR(10)
AS
BEGIN
    RETURN CASE WHEN @Price < 100 THEN 'Budget' WHEN @Price < 1000 THEN 'Mid' ELSE 'Premium' END;
END;
GO
SELECT Name, ListPrice, dbo.fn_PriceBand(ListPrice) AS Band FROM Product WHERE ListPrice > 0;

What this query does

A scalar function takes values and returns one value, and can be used inside a SELECT like a built-in function. The Day 6 price-band CASE is now written once and reused everywhere, so a change to the bands happens in one place. Scalar functions must be called with their schema (dbo.), and they run once per row, which is why the stretch below times one.

#9

9. Inline table-valued function. Parameterised view.

CREATE OR ALTER FUNCTION dbo.fn_OrdersForYear (@Year INT)
RETURNS TABLE
AS RETURN (SELECT SalesOrderID, OrderDate, TerritoryID, TotalDue FROM SalesOrderHeader WHERE YEAR(OrderDate) = @Year);
GO
SELECT TerritoryID, SUM(TotalDue) AS Revenue2013 FROM dbo.fn_OrdersForYear(2013) GROUP BY TerritoryID;

What this query does

An inline table-valued function returns a whole table from a single SELECT, so it is used in FROM like a table or view. It behaves like a view that takes parameters. SQL Server expands it into the calling query, so it is as fast as writing the SELECT directly, unlike a scalar function. The column alias is added to the plan's SUM so the result column has a name.

#10

10. TRY / CATCH with a transaction

CREATE OR ALTER PROCEDURE dbo.usp_SafeUpdate @ProductID INT, @NewPrice MONEY
AS
BEGIN
    SET NOCOUNT ON;
    BEGIN TRY
        BEGIN TRANSACTION;
        IF @NewPrice < 0 THROW 50001, 'Price cannot be negative', 1;
        UPDATE Product SET ListPrice = @NewPrice WHERE ProductID = @ProductID;
        IF @@ROWCOUNT = 0 THROW 50002, 'Product not found', 1;
        COMMIT TRANSACTION;
        PRINT 'Updated';
    END TRY
    BEGIN CATCH
        IF @@TRANCOUNT > 0 ROLLBACK TRANSACTION;
        PRINT 'Error ' + CAST(ERROR_NUMBER() AS VARCHAR(10)) + ': ' + ERROR_MESSAGE();
    END CATCH
END;
GO
EXEC dbo.usp_SafeUpdate 776, 2500;
EXEC dbo.usp_SafeUpdate 776, -1;
EXEC dbo.usp_SafeUpdate 99999, 10;

What this query does

If anything inside BEGIN TRY fails, control jumps to BEGIN CATCH. THROW raises your own error (numbers from 50000 up are free for your use). @@TRANCOUNT tells you whether a transaction is still open, so the CATCH only rolls back when there is something to undo. ERROR_NUMBER() and ERROR_MESSAGE() describe what went wrong. The three calls show each path: a good update, a rejected negative price, and a missing product, which updates 0 rows and is rolled back.

📍 The shape every load procedure should have: TRY, transaction, checks, COMMIT; CATCH, ROLLBACK, report.

Stretch

#11

See the code of a procedure

EXEC sp_helptext 'dbo.usp_GetTerritoryOrders';
SELECT name, create_date, modify_date FROM sys.procedures;

What this query does

sp_helptext prints the stored source code of a procedure, view or function, one line per row. sys.procedures lists every procedure in the database with when it was created and last changed. Useful when you inherit a database and need to know what logic lives in it.

#12

Dynamic SQL, safely

DECLARE @Table NVARCHAR(100) = 'Product', @Sql NVARCHAR(MAX);
SET @Sql = N'SELECT COUNT(*) AS RowsInTable FROM ' + QUOTENAME(@Table);
EXEC sp_executesql @Sql;

What this query does

Dynamic SQL builds a statement as text and runs it. It is needed when an object name (here a table) is only known at run time, because a table name cannot be a parameter. QUOTENAME wraps the name in [ ] so a malicious value cannot break out and inject extra SQL. For values (not names), pass real parameters to sp_executesql; never glue user input into the string.

#13

Cursor. Read it once so you recognise it.

DECLARE @Name NVARCHAR(50);
DECLARE c CURSOR FOR SELECT TOP 5 Name FROM Territory;
OPEN c; FETCH NEXT FROM c INTO @Name;
WHILE @@FETCH_STATUS = 0 BEGIN PRINT @Name; FETCH NEXT FROM c INTO @Name; END;
CLOSE c; DEALLOCATE c;

What this query does

A cursor walks through a query result one row at a time: OPEN, FETCH NEXT into variables, loop while @@FETCH_STATUS = 0 (a row was fetched), then CLOSE and DEALLOCATE to release it. It works, but it processes rows one by one, which is many times slower than a single set-based statement. Recognise it in old code; do not write new ones when a SELECT, UPDATE or MERGE can do the job.

#14

A scalar function in a WHERE on a big table. Time it.

SET STATISTICS TIME ON;
SELECT COUNT(*) AS PremiumLines FROM SalesOrderDetail WHERE dbo.fn_PriceBand(UnitPrice) = 'Premium';
SELECT COUNT(*) AS PremiumLines FROM SalesOrderDetail WHERE UnitPrice >= 1000;
SET STATISTICS TIME OFF;

What this query does

SET STATISTICS TIME ON reports CPU and elapsed time for each statement in the Messages tab. Both queries count the same order lines, but the first calls the scalar function once per row, 121,317 calls, and SQL Server cannot optimise inside it. Writing the condition inline (UnitPrice >= 1000) lets the engine evaluate it directly and, once indexes exist (Day 12), seek instead of scan.

📍 Same answer, very different cost: the function runs once for each of 121,317 rows.

Self-test

#15

Q1. A procedure that takes a year and returns revenue per territory name

CREATE OR ALTER PROCEDURE reporting.usp_RevenueByTerritory @Year INT
AS
BEGIN
    SET NOCOUNT ON;
    SELECT t.Name AS Territory, SUM(h.TotalDue) AS Revenue
    FROM SalesOrderHeader h
    JOIN Territory t ON h.TerritoryID = t.TerritoryID
    WHERE h.OrderDate >= DATEFROMPARTS(@Year, 1, 1) AND h.OrderDate < DATEFROMPARTS(@Year + 1, 1, 1)
    GROUP BY t.Name
    ORDER BY Revenue DESC;
END;
GO
EXEC reporting.usp_RevenueByTerritory @Year = 2013;

What this query does

A procedure wrapping the Day 6 join and grouping. DATEFROMPARTS builds a date from year, month and day, so the year becomes a start-inclusive, next-year-exclusive range (Day 2) instead of YEAR(OrderDate) = @Year, which would stop an index on OrderDate being used (Day 12). Territory 1 shows its Day 9 name, 'Northwest Region'.

#16

Q2. A procedure with an OUTPUT parameter returning the count of products in a colour

CREATE OR ALTER PROCEDURE dbo.usp_CountByColour @Colour NVARCHAR(15), @Products INT OUTPUT
AS
BEGIN
    SET NOCOUNT ON;
    SELECT @Products = COUNT(*) FROM Product WHERE Color = @Colour;
END;
GO
DECLARE @n INT;
EXEC dbo.usp_CountByColour @Colour = 'Red', @Products = @n OUTPUT;
SELECT 'Red' AS Colour, @n AS Products;

What this query does

The OUTPUT pattern from drill 6 again. COUNT(*) never returns NULL, so the caller always gets a number, even 0 for a colour with no products. 38 red products, as on Day 2.

#17

Q3. A function returning the days between two dates, excluding weekends

CREATE OR ALTER FUNCTION dbo.fn_WorkingDays (@Start DATE, @End DATE)
RETURNS INT
AS
BEGIN
    -- Counts Monday to Friday from @Start up to (not including) @End
    DECLARE @Days INT = DATEDIFF(day, @Start, @End);
    DECLARE @Weeks INT = @Days / 7, @Extra INT = @Days % 7;
    DECLARE @Count INT = @Weeks * 5, @d INT = 0;
    WHILE @d < @Extra
    BEGIN
        IF DATEPART(weekday, DATEADD(day, @Weeks * 7 + @d, @Start)) NOT IN (1, 7) SET @Count += 1;
        SET @d += 1;
    END;
    RETURN @Count;
END;
GO
SELECT dbo.fn_WorkingDays('2026-10-05', '2026-10-19') AS TwoWeeks,
       dbo.fn_WorkingDays('2026-10-09', '2026-10-12') AS FriToMon;

What this query does

Every full week contributes 5 working days; only the leftover 0 to 6 days need checking one by one, so the loop runs at most 6 times however far apart the dates are. DATEPART(weekday, ...) returns 1 for Sunday and 7 for Saturday under the default @@DATEFIRST of 7. The tests check the answers: two full weeks gives 10, and Friday to Monday counts only the Friday, giving 1.

📍 Assumes the default US weekday numbering (1 = Sunday, 7 = Saturday), shown by @@DATEFIRST = 7.

#18

Q4. A load procedure for reporting.ProductSales with TRY/CATCH and a row count

-- Day 10 dropped reporting.ProductSales, so recreate it first
IF OBJECT_ID('reporting.ProductSales') IS NULL
    CREATE TABLE reporting.ProductSales (
        ProductID INT NOT NULL,
        YearMonth CHAR(7) NOT NULL,
        Qty INT NOT NULL CONSTRAINT CK_ProductSales_Qty CHECK (Qty > 0),
        Revenue DECIMAL(18,2) NOT NULL,
        CONSTRAINT PK_ProductSales PRIMARY KEY (ProductID, YearMonth),
        CONSTRAINT FK_ProductSales_Product FOREIGN KEY (ProductID) REFERENCES Product(ProductID)
    );
GO
CREATE OR ALTER PROCEDURE reporting.usp_LoadProductSales
AS
BEGIN
    SET NOCOUNT ON;
    BEGIN TRY
        BEGIN TRANSACTION;
        DELETE FROM reporting.ProductSales;
        INSERT INTO reporting.ProductSales (ProductID, YearMonth, Qty, Revenue)
        SELECT d.ProductID, CONVERT(char(7), h.OrderDate, 120), SUM(d.OrderQty), SUM(d.LineTotal)
        FROM SalesOrderDetail d JOIN SalesOrderHeader h ON d.SalesOrderID = h.SalesOrderID
        GROUP BY d.ProductID, CONVERT(char(7), h.OrderDate, 120);
        DECLARE @Rows INT = @@ROWCOUNT;
        COMMIT TRANSACTION;
        SELECT @Rows AS RowsLoaded;
    END TRY
    BEGIN CATCH
        IF @@TRANCOUNT > 0 ROLLBACK TRANSACTION;
        THROW;
    END CATCH
END;

What this query does

Day 10's self-test dropped the table, so it is recreated (only if missing) with its composite key, CHECK and foreign key. The procedure uses the drill 10 shape. DELETE is used instead of TRUNCATE because it can be rolled back with everything else if the INSERT fails. @@ROWCOUNT is saved into a variable straight after the INSERT, before COMMIT resets it. In the CATCH, a bare THROW re-raises the original error, so the caller (or SSIS) sees the load failed instead of a quiet success.

#19

Q4. A load procedure for reporting.ProductSales with TRY/CATCH and a row count (continued)

-- Call it twice and prove the row count is the same both times
EXEC reporting.usp_LoadProductSales;
EXEC reporting.usp_LoadProductSales;
SELECT COUNT(*) AS RowsInTable FROM reporting.ProductSales;

What this query does

Running the load twice returns 3,862 both times, and the table holds 3,862 rows, not 7,724. The procedure is idempotent: running it again gives the same result instead of duplicates or a key error. That is the property every scheduled load needs, because jobs get re-run after failures.
