Part 1 and 2: the project and the data flow

#1

The package as the plan describes it

-- OLE SRC Sales by Territory Month (connection SRC_AdventureWorks, SQL command)
SELECT TerritoryID, FORMAT(OrderDate, 'yyyy-MM') AS YearMonth, COUNT(*) AS OrderCount, SUM(TotalDue) AS Revenue
FROM Sales.SalesOrderHeader
GROUP BY TerritoryID, FORMAT(OrderDate, 'yyyy-MM')

-- DER LoadedAt and Source:  LoadedAt = GETDATE()   Source = "SSIS"
-- OLE DST reporting SalesSummary (connection DST_AWPractice, table [reporting].[SalesSummary])

What this query does

Project AWReporting, two OLE DB connection managers (SRC_AdventureWorks and DST_AWPractice), one Data Flow Task, and inside it the three components the plan lists: an OLE DB Source running the summary query, a Derived Column adding LoadedAt and Source, and an OLE DB Destination writing to reporting.SalesSummary. The red X appears before anything runs: SSIS checks every column's data type against the target table when the package is opened (validation).

#2

The package as the plan describes it (continued)

-- F5: run the package

What this query does

FORMAT() returns nvarchar, which SSIS calls DT_WSTR (Unicode text). On Day 10 the YearMonth column was changed to VARCHAR(10), which is non-Unicode text (DT_STR). SSIS never converts between the two silently, so the destination fails validation and nothing runs. In SQL the same INSERT works because SQL Server converts implicitly; SSIS is strict about types.

📍 The plan expected this run to go green. It failed first on a data type, the error the plan calls the most common one in SSIS.

#3

The fix: a Data Conversion transform

-- DCV YearMonth to varchar:  YearMonth (DT_WSTR) -> YearMonth_vc (DT_STR, length 10, code page 1252)
-- Destination mapping:  YearMonth_vc -> YearMonth

What this query does

A Data Conversion transform creates a new column with a different data type. Here it turns the Unicode YearMonth into a non-Unicode copy, YearMonth_vc, with code page 1252 (Western European), and the destination maps YearMonth_vc onto the table's YearMonth. This is the plan's second suggested fix; the first, changing the type at the source, would also work, for example with CAST(FORMAT(...) AS varchar(7)) in the query.

#4

The fix: a Data Conversion transform (continued)

-- F5, then in SSMS:
SELECT COUNT(*) FROM AWPractice.reporting.SalesSummary;   -- 364

What this query does

Each component turns yellow while running and green when done, and every arrow shows how many rows passed along it: 364 from source to destination, one per territory per month. SELECT COUNT(*) in SSMS returns 364, matching the arrows, which is the first check after any load.

📍 Green boxes and a row count on every arrow: the Part 2 milestone. The count in SSMS matches the arrows.

Part 3: make it rerunnable

#5

Run it again. It fails on the UNIQUE constraint.

-- Shift+F5 to stop, then F5 a second time

What this query does

The second run reads the same 364 rows and tries to insert them again. The table's UNIQUE (TerritoryID, YearMonth) constraint from Day 10 rejects the duplicates. The fast-load batch is all-or-nothing, so nothing is added and the count stays 364: the constraint protected the data exactly as it was built to.

#6

Run it again. It fails on the UNIQUE constraint. (continued)

-- Progress tab (Execution Results after you stop debugging)

What this query does

The Progress tab lists every step with its errors, warnings and timings. The first red line is the real cause: an OLE DB error from the destination, which is the UNIQUE key violation. The lines after it (DTS_E_INDUCEDTRANSFORMFAILUREONERROR, DTS_E_PROCESSINPUTFAILED, task failed) are knock-on errors. The line "wrote 364 rows" is misleading: the batch was rolled back, which is why the SSMS count stays 364.

📍 The Progress tab is where you look when a package fails. Read the first red line, not the last.

#7

The fix: an Execute SQL Task that truncates first

-- SQL Truncate Target (Execute SQL Task, connection DST_AWPractice)
TRUNCATE TABLE reporting.SalesSummary;
-- green arrow (precedence constraint: Success) -> DFT Load Sales Summary

What this query does

The Control Flow canvas holds tasks and the order they run in. The green arrow is a precedence constraint on Success: the data flow starts only if the truncate succeeded. Emptying the table before loading it is the Day 10 'delete then insert' pattern, now inside the package.

#8

The fix: an Execute SQL Task that truncates first (continued)

-- F5, check the count, Shift+F5, F5 again, check the count again

What this query does

First run: truncate, then load 364 rows. Both tasks green.

#9

The fix: an Execute SQL Task that truncates first (continued)

SELECT COUNT(*) FROM AWPractice.reporting.SalesSummary;   -- 364 after run 1, 364 after run 2

What this query does

Second run: still green, still 364 rows. A scheduled load gets re-run after every failure, every server restart and every manual retry, so this property is what makes it safe to automate.

📍 The package is idempotent: running it twice gives the same result as running it once.

Stretch

#10

Lookup the territory name, redirect no-match rows, count the rows

-- LKP Territory Name (Lookup, connection DST_AWPractice)
SELECT TerritoryID, Name AS TerritoryName FROM dbo.Territory
-- join on TerritoryID, add TerritoryName; no-match rows -> reporting.SalesSummary_Unmatched
-- CNT Rows Loaded (Row Count) -> package variable User::RowsLoaded

ALTER TABLE reporting.SalesSummary ADD TerritoryName NVARCHAR(50) NULL;
CREATE TABLE reporting.SalesSummary_Unmatched (TerritoryID INT NULL, YearMonth NVARCHAR(10) NULL,
    OrderCount INT NULL, Revenue DECIMAL(18,2) NULL, LoadedAt DATETIME2 NOT NULL DEFAULT SYSDATETIME());

What this query does

A Lookup works like a LEFT JOIN inside the data flow: for each row it looks up TerritoryID in dbo.Territory and adds the TerritoryName column. Rows with no match would make the whole load fail by default; setting 'redirect rows to no match output' sends them to their own table instead, so bad rows are kept for checking rather than lost or fatal. The Row Count transform counts the rows passing through and stores the total in a package variable.

#11

Lookup the territory name, redirect no-match rows, count the rows (continued)

SELECT COUNT(*), COUNT(TerritoryName) FROM reporting.SalesSummary;   -- 364, 364
SELECT COUNT(*) FROM reporting.SalesSummary_Unmatched;               -- 0

What this query does

Every TerritoryID from AdventureWorks exists in AWPractice.dbo.Territory, so all 364 rows match, all 364 get a TerritoryName and the unmatched table stays empty. RowsLoaded = 364. Territory 1 shows 'Northwest Region', the name the Day 9 MERGE gave it, which proves the lookup reads AWPractice, not AdventureWorks.

Part 4: add a file source

#12

LoadTerritories as the plan describes it: CSV straight into dbo.Territory

-- territories.csv: Sales.SalesTerritory exported with column names in the first row, plus
-- 11,Pakistan,PK,Asia,0,0,0,0,<new GUID>,<today>
-- Flat File Source (TerritoryID DT_I4, money columns DT_CY, rowguid DT_GUID, ModifiedDate DT_DBTIMESTAMP)
--   -> OLE DB Destination [dbo].[Territory] (keep identity)

What this query does

A Flat File connection manager describes the CSV: delimiter, header row, and the data type of each column, set on its Advanced tab. TerritoryID is DT_I4 (4-byte integer) as the plan says, rather than text. The warning on the destination is about CountryRegionCode: a 50-character file column going into a 3-character table column could be cut short.

LoadTerritories as the plan describes it: CSV straight into dbo.Territory (continued)

-- F5

What this query does

The run fails on the very first component, the file source, before any row reaches the database. 'OLE DST dbo Territory wrote 0 rows'.

#14

LoadTerritories as the plan describes it: CSV straight into dbo.Territory (continued)

-- Progress tab

What this query does

The rowguid column was set to DT_GUID, but in a text file a GUID is plain text without the {curly braces} that SSIS expects when parsing one, so every row fails conversion at row 2. The fix the plan gives is to change the type on the Flat File connection's Advanced tab: rowguid becomes DT_WSTR (text), 50 characters.

📍 Exactly the data-type failure the plan predicts. The cause is the GUID format, not the TerritoryID.

#15

The working version: stage, then MERGE

-- SQL Truncate Staging
TRUNCATE TABLE dbo.TerritoryStaging;
-- DFT Load Territories: territories.csv (rowguid now DT_WSTR) -> dbo.TerritoryStaging
-- SQL Merge into Territory
SET IDENTITY_INSERT dbo.Territory ON;
MERGE dbo.Territory AS target
USING dbo.TerritoryStaging AS source ON target.TerritoryID = source.TerritoryID
WHEN MATCHED THEN UPDATE SET target.Name = source.Name, target.CountryRegionCode = source.CountryRegionCode, target.[Group] = source.[Group]
WHEN NOT MATCHED THEN INSERT (TerritoryID, Name, CountryRegionCode, [Group], SalesYTD, SalesLastYear, CostYTD, CostLastYear, rowguid, ModifiedDate)
     VALUES (source.TerritoryID, source.Name, source.CountryRegionCode, source.[Group], 0, 0, 0, 0, NEWID(), GETDATE());
SET IDENTITY_INSERT dbo.Territory OFF;

What this query does

Fixing the type is not enough for the plan's version: AWPractice.dbo.Territory already holds territories 1 to 11 from Day 9 with a primary key since Day 10, so loading the same IDs again would fail on the key, and even the first run would only work once. The standard pattern for files is to land them in a staging table, then MERGE into the real table (Day 9): matched rows are updated, new rows inserted. The package runs truncate staging, load file, merge, in that order, joined by green Success arrows.

📍 Inserting straight into dbo.Territory could never be re-run: territories 1 to 11 already exist and the primary key from Day 10 would reject them.

#16

The working version: stage, then MERGE (continued)

SELECT COUNT(*) FROM dbo.TerritoryStaging;          -- 11
SELECT TerritoryID, Name FROM dbo.Territory;         -- 1 is 'Northwest' again; 11 Pakistan; 14 Bangladesh kept

What this query does

All three tasks are green. The 11 file rows landed in staging, and the MERGE updated territories 1 to 11: territory 1 is 'Northwest' again (the file's name replaces the Day 9 'Northwest Region'), Pakistan is confirmed as territory 11, and Bangladesh (14), which is not in the file, is left untouched because the MERGE has no WHEN NOT MATCHED BY SOURCE clause. The package can be run any number of times.

Self-test

The four things every package had: a connection manager, a source, a transform, a destination.
Why the first rerun failed: the UNIQUE key on (TerritoryID, YearMonth) rejected rows that were already there; fixed by truncating first, so the package is idempotent.
Where to look when a package fails: the Progress tab (Execution Results after you stop debugging), first red line.
Data Conversion transform: makes a copy of a column with a different SSIS data type, most often Unicode to non-Unicode text.
Green arrow between Control Flow tasks: a precedence constraint on Success; the next task runs only if the previous one succeeded.
Not done on this PC: deploying to SSISDB and running from the catalog needs Integration Services on a paid SQL Server edition, and the Script Task stretch needs the designer's script editor. Replacing the data flow with EXEC reporting.usp_LoadSalesSummary is a one-line Execute SQL Task; a procedure is the better choice when source and target are on the same server, while a data flow earns its place across servers or with files.
