Day 19: Star schema and snowflake schema

Fri 23 October 2026 · 15 queries · run on AdventureWorksDW2022 and AWPractice

Goal: draw both, say when each is used, and recognise that AdventureWorksDW is a mix.

Read: Kimball Group "Star schema" and "Snowflake" summary pages. Microsoft Learn "Understand star schema and the importance for Power BI", in full.

StarSnowflake
ShapeOne fact in the middle; each dimension is one flat table joined directly to itDimensions normalised into chains: DimProduct to DimProductSubcategory to DimProductCategory
JoinsOne per dimension usedOne per level of each chain
Repeated dataSome: "Bikes" is stored on every bike row of DimProductNone: each category name is stored once
For usersSimple: every attribute of a product is in the product tableHarder: users must know which table holds Category
When usedThe default, and what Power BI expectsA huge dimension, or a sub-dimension shared by several dimensions (DimGeography is used by both DimCustomer and DimReseller)
AdventureWorksDW is a mix: each fact table is the centre of a star, and three dimensions grow snowflake chains (product, customer geography, employee territory). The drills find both from the system catalog.

Drill: find both in AdventureWorksDW

#1

1. Every foreign key: the schema diagram as data

USE AdventureWorksDW2022;
SELECT fk.name AS FK, OBJECT_NAME(fk.parent_object_id) AS FromTable, OBJECT_NAME(fk.referenced_object_id) AS ToTable
FROM sys.foreign_keys fk ORDER BY FromTable, ToTable;

What this query does

44 foreign keys. Read top to bottom, the Dim rows come first: a dimension pointing at another dimension is a snowflake link, and a table pointing at itself (DimAccount, DimEmployee, DimOrganization, DimDepartmentGroup) is a parent-child hierarchy. Then the Fact rows: each one is an arm of a star. FactInternetSales and FactResellerSales each point at DimDate three times (FK_..._DimDate, DimDate1, DimDate2: order, due, ship).

📍 A database diagram is just this list drawn as boxes and lines.

#2

2. The star part: what FactInternetSales joins to directly

SELECT OBJECT_NAME(fk.referenced_object_id) AS Dimension
FROM sys.foreign_keys fk WHERE OBJECT_NAME(fk.parent_object_id) = 'FactInternetSales';

What this query does

Eight foreign keys to six dimensions: DimCurrency, DimCustomer, DimDate (three times), DimProduct, DimPromotion, DimSalesTerritory. Each is one join away from the fact: that is the star.

📍 Six points on the star; DimDate is used three times in different roles.

#3

3. The snowflake part: dimensions that point at other dimensions

SELECT OBJECT_NAME(fk.parent_object_id) AS Dimension, OBJECT_NAME(fk.referenced_object_id) AS PointsTo
FROM sys.foreign_keys fk
WHERE OBJECT_NAME(fk.parent_object_id) LIKE 'Dim%' AND OBJECT_NAME(fk.referenced_object_id) LIKE 'Dim%';

What this query does

11 rows. Four are self-references (DimAccount, DimDepartmentGroup, DimEmployee, DimOrganization point at themselves for parent-child hierarchies), which are not snowflakes. The real chains: DimProduct to DimProductSubcategory to DimProductCategory; DimCustomer to DimGeography to DimSalesTerritory; DimReseller to DimGeography; DimEmployee to DimSalesTerritory; DimOrganization to DimCurrency. The syllabus names three; the query shows DimGeography itself also points on to DimSalesTerritory, so the customer chain is three tables long.

📍 AdventureWorksDW is a star at the fact and a snowflake around product, geography and territory.

#4

4. Flatten the product snowflake into a view

CREATE OR ALTER VIEW dbo.vw_DimProductFlat AS
SELECT p.ProductKey, p.EnglishProductName AS Product, p.Color, p.Size, p.ListPrice,
       ps.EnglishProductSubcategoryName AS Subcategory, pc.EnglishProductCategoryName AS Category
FROM DimProduct p
LEFT JOIN DimProductSubcategory ps ON p.ProductSubcategoryKey = ps.ProductSubcategoryKey
LEFT JOIN DimProductCategory pc ON ps.ProductCategoryKey = pc.ProductCategoryKey;

What this query does

The view does the two snowflake joins once, so users see one flat product table with Subcategory and Category as columns: a star-shaped dimension. The joins are LEFT JOINs because 209 of the 606 products have no subcategory (components and older items); an INNER JOIN would silently drop them from the dimension. CREATE OR ALTER makes the script re-runnable (Day 10).

📍 This is what you hand to Power BI: one product table, one relationship to the fact.

#5

5. Day 18 drill 2 through the view: one join instead of three

SELECT v.Category, SUM(f.SalesAmount) AS Revenue
FROM FactInternetSales f JOIN dbo.vw_DimProductFlat v ON f.ProductKey = v.ProductKey
GROUP BY v.Category ORDER BY Revenue DESC;

What this query does

Same three categories and the same totals as Day 18 drill 2 (Bikes 28.32 million, Accessories 0.70 million, Clothing 0.34 million). The query names one dimension. Products without a category would appear under NULL; none of them was ever sold online, so there is no NULL row.

📍 Fewer joins for the person writing the query. Whether the server does less work is the next question.

#6

6. Cost of the snowflake: the plan for three joins

SELECT pc.EnglishProductCategoryName AS Category, SUM(f.SalesAmount) AS Revenue
FROM FactInternetSales f
JOIN DimProduct p ON f.ProductKey = p.ProductKey
JOIN DimProductSubcategory ps ON p.ProductSubcategoryKey = ps.ProductSubcategoryKey
JOIN DimProductCategory pc ON ps.ProductCategoryKey = pc.ProductCategoryKey
GROUP BY pc.EnglishProductCategoryName ORDER BY Revenue DESC;

What this query does

Include Actual Execution Plan (Ctrl+M) is on. Three join operators, one per link: a Nested Loops joins subcategory to category (37 rows), and two Merge Joins bring in DimProduct and the fact (the lower branch, scrolled out of view). The optimizer is clever here: it first aggregates FactInternetSales by ProductKey (a Hash Match aggregate turns 60,398 rows into about 160), then joins the small result to the dimensions. Estimated cost 1.55.

📍 Count the join operators in the plan: one per table after the first.

#7

7. The view version of the same plan

SELECT v.Category, SUM(f.SalesAmount) AS Revenue
FROM FactInternetSales f JOIN dbo.vw_DimProductFlat v ON f.ProductKey = v.ProductKey
GROUP BY v.Category ORDER BY Revenue DESC;

What this query does

The query text has one join, but the plan still joins all four tables: SQL Server expands the view into its definition before optimising. It is also more expensive (estimated cost 2.45 against 1.55, about 57% more): the view's LEFT JOINs become outer joins (Nested Loops Left Outer, Hash Match Right Outer), which limit how the optimizer can reorder them, so it no longer aggregates the fact first and hashes all 60,398 rows instead. It even suggests a missing index. A view saves typing and mistakes, not work. Only a physically flat dimension (Category stored as a column in DimProduct, which is what a star means) removes the joins at query time.

📍 A view flattens the model for people; a flattened table flattens it for the server too.

#8

8. Cost of the star: how much text flattening would repeat

SELECT COUNT(*) AS Customers, COUNT(DISTINCT GeographyKey) AS DistinctGeographies,
       COUNT(*) * 1.0 / COUNT(DISTINCT GeographyKey) AS CustomersPerGeography,
       (SELECT COUNT(*) FROM DimGeography) AS GeographyRows
FROM DimCustomer;

What this query does

18,484 customers live in only 336 distinct geographies (DimGeography has 655 rows; the rest belong to resellers or nobody). The syllabus comment says about 650 and 28 repeats; the real figure is about 55 customers per geography, so flattening city, state and country into DimCustomer repeats each city name about 55 times. That is still only a few hundred kilobytes: disk is cheap, joins are not.

📍 Check the syllabus' estimates against the data: here the repetition is double what was predicted, and the conclusion still holds.

#9

9. Conformed dimension: one DimDate shared by every fact

SELECT OBJECT_NAME(fk.parent_object_id) AS Fact, COUNT(*) AS DateKeys
FROM sys.foreign_keys fk WHERE OBJECT_NAME(fk.referenced_object_id) = 'DimDate' GROUP BY OBJECT_NAME(fk.parent_object_id);

What this query does

Eight fact tables point at the same DimDate: call centre, currency rates, finance, internet sales (3 keys), inventory, reseller sales (3 keys), sales quotas and survey responses. Because they share one date table, "2013" or "Q4" means the same days in every report, and Day 18 drill 6 could stack internet and reseller revenue by year safely.

📍 A conformed dimension is one dimension table used by several facts, with the same keys and the same meaning.

11. The same diagram with DimProductSubcategory and DimProductCategory

What this query does

Adding the two product tables grows a branch on the right: DimProduct to DimProductSubcategory to DimProductCategory, each pointing at the next through ProductSubcategoryKey and ProductCategoryKey. Category is now three lines away from the fact instead of one. That branch is the snowflake.

📍 A star grows a branch: that branch is a snowflake.

Written exercise: the ride model as a star and as a snowflake

#12

12. Pure star: Zone and City in one table, Vehicle folded into the driver

USE AWPractice;
DROP TABLE IF EXISTS dbo.StarLocation, dbo.StarDriver;
SELECT ZoneKey AS LocationKey, ZoneName AS Zone, City INTO StarLocation FROM DimZone;
SELECT DISTINCT d.DriverKey, d.DriverName, v.VehiclePlate, v.VehicleType
INTO StarDriver
FROM FactRide f JOIN DimDriver d ON d.DriverKey = f.DriverKey JOIN DimVehicle v ON v.VehicleKey = f.VehicleKey;
SELECT * FROM StarLocation; SELECT * FROM StarDriver;

What this query does

Built from the Day 17 dimensions. StarLocation holds zone and city together (6 rows; Lahore repeats four times). StarDriver holds each driver with the vehicle they drove (4 rows). Keys are kept equal to the Day 17 keys so FactRide can join to them unchanged.

📍 Each dimension is one flat table, one join from the fact.

#13

13. Fare by city by month on the star: 2 joins

SELECT l.City, d.CalendarYear, d.MonthName, SUM(f.FareAmount) AS Fare
FROM FactRide f
JOIN StarLocation l ON l.LocationKey = f.PickupZoneKey
JOIN DimRideDate d ON d.DateKey = f.DateKey
GROUP BY l.City, d.CalendarYear, d.MonthName;

What this query does

Lahore 1,330 and Karachi 700 in October 2026 (the five rides add up to 2,030). Two joins: one to location for the city, one to date for the month.

📍 Star: one join per dimension used.

#14

14. Snowflake: Zone points to City, Driver to Vehicle to VehicleType

DROP TABLE IF EXISTS dbo.SnowDriver, dbo.SnowVehicle, dbo.SnowVehicleType, dbo.SnowZone, dbo.SnowCity;
SELECT IDENTITY(INT, 1, 1) AS CityKey, City INTO SnowCity FROM (SELECT DISTINCT City FROM DimZone) c;
SELECT z.ZoneKey, z.ZoneName, c.CityKey INTO SnowZone FROM DimZone z JOIN SnowCity c ON c.City = z.City;
SELECT IDENTITY(INT, 1, 1) AS VehicleTypeKey, VehicleType INTO SnowVehicleType FROM (SELECT DISTINCT VehicleType FROM DimVehicle) t;
SELECT v.VehicleKey, v.VehiclePlate, t.VehicleTypeKey INTO SnowVehicle FROM DimVehicle v JOIN SnowVehicleType t ON t.VehicleType = v.VehicleType;
SELECT DISTINCT f.DriverKey, d.DriverName, f.VehicleKey INTO SnowDriver FROM FactRide f JOIN DimDriver d ON d.DriverKey = f.DriverKey;
SELECT 'SnowCity' AS T, COUNT(*) AS Rows FROM SnowCity UNION ALL SELECT 'SnowZone', COUNT(*) FROM SnowZone
UNION ALL SELECT 'SnowVehicleType', COUNT(*) FROM SnowVehicleType UNION ALL SELECT 'SnowVehicle', COUNT(*) FROM SnowVehicle
UNION ALL SELECT 'SnowDriver', COUNT(*) FROM SnowDriver;

What this query does

The same information normalised into five tables: 2 cities, 6 zones (each pointing at a city), 3 vehicle types, 4 vehicles (each pointing at a type) and 4 drivers (each pointing at a vehicle). Nothing is repeated: "Lahore" is stored once instead of four times, "Mini" once instead of twice.

📍 Snowflake: no repeated text, but each level is another table.

#15

15. Fare by city by month on the snowflake: 3 joins

SELECT c.City, d.CalendarYear, d.MonthName, SUM(f.FareAmount) AS Fare
FROM FactRide f
JOIN SnowZone z ON z.ZoneKey = f.PickupZoneKey
JOIN SnowCity c ON c.CityKey = z.CityKey
JOIN DimRideDate d ON d.DateKey = f.DateKey
GROUP BY c.City, d.CalendarYear, d.MonthName;

What this query does

Same answer, one join more: the city is two steps from the fact. A question about vehicle type would need three joins on the snowflake (driver, vehicle, type) against one on the star.

📍 I would ship the star (reasons below the queries).

Written exercise: the ride model twice

STAR: zone and city in one table, vehicle folded into the driver

  StarLocation (LocationKey, Zone, City)   x2: pickup, dropoff
           |
  DimRideDate -- FactRide -- StarDriver (DriverKey, DriverName, VehiclePlate, VehicleType)
           |
  DimRider, DimPayment

  Fare by city by month:  FactRide -> StarLocation -> City
                          FactRide -> DimRideDate  -> MonthName      = 2 joins
SNOWFLAKE: zone points to city, driver to vehicle to vehicle type

  SnowCity (CityKey, City)
      ^
  SnowZone (ZoneKey, ZoneName, CityKey)   x2: pickup, dropoff
      |
  DimRideDate -- FactRide -- SnowDriver (DriverKey, DriverName, VehicleKey)
                                  -> SnowVehicle (VehicleKey, VehiclePlate, VehicleTypeKey)
                                      -> SnowVehicleType (VehicleTypeKey, VehicleType)

  Fare by city by month:  FactRide -> SnowZone -> SnowCity -> City
                          FactRide -> DimRideDate -> MonthName       = 3 joins
Which I would ship: the star. City and vehicle type are tiny (2 cities, 3 vehicle types), so folding them in repeats a few words while saving a join on every city or vehicle question and giving Power BI users one table per subject; I would only snowflake if a level were large or shared by several dimensions.

Self-test: answers

A star from memory with five dimensions:
                 DimDate
                    |
  DimCustomer -- FactSales -- DimProduct
                 /       \
         DimStore         DimPromotion

  FactSales: DateKey, CustomerKey, ProductKey, StoreKey, PromotionKey,
             Quantity, SalesAmount, Cost
Three snowflake chains in AdventureWorksDW: DimProduct to DimProductSubcategory to DimProductCategory; DimCustomer to DimGeography (to DimSalesTerritory); DimEmployee to DimSalesTerritory. (DimReseller to DimGeography and DimOrganization to DimCurrency are two more.)

Conformed dimension: one dimension table shared by several fact tables with the same keys and meaning, so their results can be compared and combined: DimDate is used by eight facts.

When snowflaking is worth it, in one line: when a dimension level is very large or is shared by several dimensions and must be maintained in one place.

Why Power BI prefers stars: each dimension becomes one table with one relationship to the fact, so filters flow in one direction with no chains; users find every attribute where they expect it; and fewer relationships make the model smaller and faster to query.
