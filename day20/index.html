Day 20: Slowly changing dimensions, the date dimension, surrogate keys

Mon 26 October 2026 · 20 queries · run on AdventureWorksDW2022 and AWPractice

Goal: the three things that separate a textbook star from one that survives a year of real data.

Read: Kimball Group "Slowly changing dimension techniques" (Types 0 to 7; Types 1 and 2 in depth), "Calendar date dimensions" and "Dimension surrogate keys".

Why this day matters: a textbook star schema works on day one. These three ideas keep it working after a year of real data, when customers move, prices change and source systems renumber their records.
IdeaThe problem it solvesIn one line
Slowly changing dimension (SCD)A customer moves city. Should last year's sales show the old city or the new one?Decide, per column, whether to overwrite (Type 1) or keep history (Type 2).
Date dimensionEvery report needs year, month, weekday, fiscal period and holidays, and calculating them in every query is slow and error-prone.One row per calendar day with every attribute pre-computed.
Surrogate keySource IDs can change, be reused, clash between systems, or stop being unique once history is kept.An integer the warehouse itself assigns; facts store only this.

What happensUPDATE the existing rowClose the old row (end date, IsCurrent = 0) and INSERT a new row with a new surrogate key

Slowly changing dimensions: Type 2 in AdventureWorksDW

#1

1. Type 2 in the wild: one product, three rows, three price periods

USE AdventureWorksDW2022;
SELECT ProductKey, ProductAlternateKey, EnglishProductName, ListPrice, StartDate, EndDate, Status
FROM DimProduct WHERE ProductAlternateKey = 'FR-M94B-38' ORDER BY StartDate;

What this query does

ProductAlternateKey FR-M94B-38 is the natural key: the product code the business uses. It appears three times, with three different surrogate keys (304, 305, 306) and three list prices (1,191.17, then 1,226.91, then 1,349.60). Each time the price changed, the warehouse did not overwrite the row: it added a new one. That is a Type 2 slowly changing dimension. Only the newest row has Status = 'Current' and no EndDate. The older rows' EndDates (2007 and 2008) come before their StartDates (2011 and 2012): the same data fault found on Day 16, so never trust the date order here.

📍 Same product, three rows: the warehouse kept every price it ever had.

#2

2. The current row only

SELECT * FROM DimProduct WHERE ProductAlternateKey = 'FR-M94B-38' AND EndDate IS NULL;

What this query does

One row: ProductKey 306, the version in force today. "EndDate IS NULL" (or Status = 'Current', or an IsCurrent flag in other warehouses) is how every Type 2 dimension marks the live row. Use it when the question is "what is true now", such as today's price list.

📍 Type 2 question one: what is true now? Filter on the open row.

#3

3. Each sale is joined to the price in force at the time

SELECT p.ProductKey, p.ListPrice AS PriceAtTime, p.StartDate, p.EndDate, COUNT(*) AS Lines, SUM(f.SalesAmount) AS Revenue
FROM FactResellerSales f JOIN DimProduct p ON f.ProductKey = p.ProductKey
WHERE p.ProductAlternateKey = 'FR-M94B-38' GROUP BY p.ProductKey, p.ListPrice, p.StartDate, p.EndDate;

What this query does

289 sales lines in total, split by version: 71 lines (92,196.85) under key 304, 113 lines (195,814.70) under key 305 and 105 lines (213,776.64) under key 306. No date logic is needed: when a sale was loaded, the load stored the surrogate key of the version in force that day, so a plain join on ProductKey returns the price at the time. Resellers paid exactly 60% of each version's list price (714.70, 736.15, 809.76 per unit).

📍 Type 2 question two: what was true then? The surrogate key in the fact already answers it.

#4

4. How much history does DimProduct keep?

SELECT COUNT(*) AS DimRows, COUNT(DISTINCT ProductAlternateKey) AS Products,
       SUM(CASE WHEN EndDate IS NULL THEN 1 ELSE 0 END) AS OpenRows,
       COUNT(*) - COUNT(DISTINCT ProductAlternateKey) AS ExtraHistoryRows
FROM DimProduct;

What this query does

606 rows describe 504 real products, so 102 rows exist only to keep history. 406 rows are open (no EndDate). The other 98 products have no open row at all: they were discontinued, and their last version was closed. This is also why Day 16 found duplicate ProductAlternateKeys: they are not duplicates, they are versions.

📍 Duplicates of the natural key in a dimension usually mean Type 2 history, not bad data.

Build Type 2 yourself: the rider dimension in AWPractice

#5

5. The syllabus script first: CREATE TABLE DimRider

USE AWPractice;
CREATE TABLE DimRider (
    RiderKey INT IDENTITY PRIMARY KEY,        -- surrogate
    RiderPhone VARCHAR(20) NOT NULL,           -- natural key
    RiderName VARCHAR(50), RiderCity VARCHAR(50),
    EffectiveFrom DATE NOT NULL, EffectiveTo DATE NULL, IsCurrent BIT NOT NULL DEFAULT 1
);

What this query does

It fails: DimRider already exists, because Day 17 built it for the ride-sharing star, and FactRide points at it with a foreign key. Dropping it would break FactRide. A real warehouse has the same problem when it decides a dimension needs history after it is already in use, so the next step changes the existing table instead.

📍 Read the error, then adapt: the table is already there, so alter it rather than recreate it.

#6

6. Turn the existing DimRider into a Type 2 dimension

IF COL_LENGTH('dbo.DimRider', 'IsCurrent') IS NULL          -- only the first time (re-runnable)
    ALTER TABLE dbo.DimRider ADD
        EffectiveFrom DATE NOT NULL CONSTRAINT DF_DimRider_From DEFAULT '2026-01-01',
        EffectiveTo   DATE NULL,
        IsCurrent     BIT  NOT NULL CONSTRAINT DF_DimRider_Current DEFAULT 1;
SELECT * FROM DimRider;

What this query does

Three new columns. Because EffectiveFrom and IsCurrent are NOT NULL with a DEFAULT, SQL Server fills them in for the three existing riders: every row is valid from 1 January 2026 and is the current row. EffectiveTo is empty (NULL), meaning "still valid". RiderKey is still the IDENTITY surrogate key from Day 17, and RiderPhone is the natural key that identifies a person. The IF line makes the script safe to run twice.

📍 A Type 2 dimension needs three things: a valid-from date, a valid-to date and a current flag.

#7

7. Ayesha moves to Islamabad on 15 October: close the old row, add a new one

SET XACT_ABORT ON;     -- any error cancels the whole transaction
IF NOT EXISTS (SELECT 1 FROM DimRider WHERE RiderPhone = '0300-1111111' AND RiderCity = 'Islamabad')
BEGIN
    BEGIN TRANSACTION;
    UPDATE DimRider SET EffectiveTo = '2026-10-14', IsCurrent = 0
    WHERE RiderPhone = '0300-1111111' AND IsCurrent = 1;
    INSERT INTO DimRider (RiderPhone, RiderName, RiderCity, EffectiveFrom)
    VALUES ('0300-1111111', 'Ayesha', 'Islamabad', '2026-10-15');
    COMMIT;
END
SELECT * FROM DimRider ORDER BY RiderPhone, EffectiveFrom;

What this query does

It fails: "Violation of UNIQUE KEY constraint". On Day 17, RiderPhone was given a UNIQUE constraint, which was right while the table held one row per person. A Type 2 dimension must allow several rows per person, so that rule now blocks the change. The first time I ran this without SET XACT_ABORT ON, the UPDATE succeeded, the INSERT failed and COMMIT saved the UPDATE anyway: Ayesha was left with no current row at all. Here the Messages tab shows "(1 row affected)" for the UPDATE, then the error from the INSERT. With XACT_ABORT ON, the error rolled back the whole transaction, including that UPDATE, so the table is unchanged.

📍 Making a dimension Type 2 changes its rules: the natural key is no longer unique.

#8

8. Replace the rule: one CURRENT row per phone number

DECLARE @uq sysname = (SELECT name FROM sys.key_constraints
                       WHERE parent_object_id = OBJECT_ID('dbo.DimRider') AND type = 'UQ');
IF @uq IS NOT NULL EXEC('ALTER TABLE dbo.DimRider DROP CONSTRAINT ' + @uq);
IF NOT EXISTS (SELECT 1 FROM sys.indexes WHERE name = 'UX_DimRider_CurrentPhone')
    CREATE UNIQUE INDEX UX_DimRider_CurrentPhone ON dbo.DimRider (RiderPhone) WHERE IsCurrent = 1;
SELECT name, type_desc, is_unique, filter_definition FROM sys.indexes WHERE object_id = OBJECT_ID('dbo.DimRider');

What this query does

Day 17's constraint had a name SQL Server made up (UQ__DimRider__08B9...), so the script looks it up in sys.key_constraints and drops it with dynamic SQL (Day 11). In its place goes a filtered unique index: RiderPhone must be unique only among rows WHERE IsCurrent = 1. A rider may have any number of closed rows but never two current ones, which is exactly the rule a Type 2 dimension needs. The table now has two indexes: the primary key on RiderKey and the new filtered index.

📍 A Type 2 dimension's rule is "one current row per natural key", not "one row per natural key".

#9

9. The same change again: now it works

SET XACT_ABORT ON;     -- any error cancels the whole transaction
IF NOT EXISTS (SELECT 1 FROM DimRider WHERE RiderPhone = '0300-1111111' AND RiderCity = 'Islamabad')
BEGIN
    BEGIN TRANSACTION;
    UPDATE DimRider SET EffectiveTo = '2026-10-14', IsCurrent = 0
    WHERE RiderPhone = '0300-1111111' AND IsCurrent = 1;
    INSERT INTO DimRider (RiderPhone, RiderName, RiderCity, EffectiveFrom)
    VALUES ('0300-1111111', 'Ayesha', 'Islamabad', '2026-10-15');
    COMMIT;
END
SELECT * FROM DimRider ORDER BY RiderPhone, EffectiveFrom;

What this query does

Ayesha now has two rows. RiderKey 1 (Lahore) is closed: valid until 14 October, IsCurrent 0. Her new row (Islamabad) is valid from 15 October with IsCurrent 1 and no EffectiveTo. Its key is 6, not 2 as in the syllabus: Bilal and Sara already hold 2 and 3, and the failed attempts in step 7 used up identity numbers (IDENTITY never gives a number back, even after a rollback). The UPDATE and INSERT ran as one transaction (Day 9).

📍 Type 2 change = UPDATE the old row to close it + INSERT a new row. Never overwrite.

#10

10. Lookup at load time: which RiderKey does a new ride get?

SELECT r.RideDate, d.RiderKey, d.RiderCity
FROM (VALUES (CAST('2026-10-01' AS DATE)), ('2026-10-20')) AS r(RideDate)
JOIN DimRider d ON d.RiderPhone = '0300-1111111'
 AND r.RideDate BETWEEN d.EffectiveFrom AND ISNULL(d.EffectiveTo, '9999-12-31');

What this query does

The ETL receives a ride with a phone number and a date, and must store a RiderKey. The BETWEEN finds the version valid on the ride date: a ride on 1 October gets RiderKey 1 (Lahore) and a ride on 20 October gets RiderKey 6 (Islamabad). ISNULL turns the open end date into a far-future date so the current row matches any date from 15 October on. This is the lookup an SSIS package would do (Day 13's Lookup transformation, with a date range).

📍 Fact loads look up the surrogate key by natural key AND date.

#11

11. Her old rides keep her old city

SELECT f.RideID, f.PickupTime, r.RiderKey, r.RiderName, r.RiderCity, f.FareAmount
FROM FactRide f JOIN DimRider r ON r.RiderKey = f.RiderKey
WHERE r.RiderPhone = '0300-1111111';

What this query does

Ayesha's two rides on 1 October were stored with RiderKey 1, so they still report Lahore after her move. "Revenue by rider city for October 1" gives the same answer today as it did before she moved. That is the whole point of Type 2: history does not change when the present does.

📍 Old facts point at old rows, so old reports stay correct.

#12

12. What Type 1 would have done: rewrite history

SELECT f.RideID, f.PickupTime, r.RiderCity AS CityAtTimeOfRide, cur.RiderCity AS CityIfOverwritten
FROM FactRide f
JOIN DimRider r   ON r.RiderKey = f.RiderKey
JOIN DimRider cur ON cur.RiderPhone = r.RiderPhone AND cur.IsCurrent = 1
WHERE r.RiderPhone = '0300-1111111';

What this query does

This shows, without changing any data, what a Type 1 overwrite would report. The second join finds her current row, which is what a single overwritten row would hold. Rides taken in Lahore would show Islamabad, and Lahore's October revenue would silently drop by 970. Type 1 is right only when the old value was wrong (a typo), not when it was true and changed.

📍 Type 1 moves old facts to the new value. Fine for corrections, wrong for real changes.

#13

13. Type 1 for a correction: fix her name everywhere

UPDATE DimRider SET RiderName = 'Ayesha Khan' WHERE RiderPhone = '0300-1111111';
SELECT RiderKey, RiderPhone, RiderName, RiderCity, EffectiveFrom, EffectiveTo, IsCurrent FROM DimRider;

What this query does

A spelling fix is not history; nobody wants a report that says she was called "Ayesha" before October. So the name is overwritten in place, on both of her rows (the WHERE matches the phone number, not the current row). One table can mix both types: RiderCity is tracked as Type 2, RiderName as Type 1.

📍 Decide the type per column, not per table.

The date dimension

#14

14. Read the real one

USE AdventureWorksDW2022;
SELECT TOP 5 * FROM DimDate WHERE CalendarYear = 2013 AND MonthNumberOfYear = 7;

What this query does

One row per day. DateKey is an integer in the form yyyymmdd (20130701). The other 18 columns are pre-computed: day and month names in English, Spanish and French, day of week, month and year, week number, month number, calendar quarter, year and semester, and fiscal quarter, year and semester. A query that needs "Mondays in fiscal Q1" filters these columns instead of calculating anything.

📍 Work done once, in the dimension, so no report ever has to compute it.

#15

15. How many days does it cover?

SELECT COUNT(*) AS Days, MIN(FullDateAlternateKey) AS FirstDay, MAX(FullDateAlternateKey) AS LastDay FROM DimDate;

What this query does

3,652 rows: every day from 1 January 2005 to 31 December 2014, ten full years including leap days. A date dimension covers every day, even days with no sales, so a report can show a zero for a quiet day instead of leaving it out.

📍 A date dimension has every day, not just the days with facts.

#16

16. Build my own for 2026 in AWPractice

USE AWPractice;
DROP TABLE IF EXISTS dbo.DimDate;
CREATE TABLE DimDate (
    DateKey INT PRIMARY KEY, FullDate DATE NOT NULL, Year INT, Quarter INT, Month INT, MonthName VARCHAR(10),
    Day INT, DayOfWeek INT, DayName VARCHAR(10), IsWeekend BIT, WeekOfYear INT, FiscalYear INT, FiscalQuarter INT
);
;WITH Dates AS (
    SELECT CAST('2026-01-01' AS DATE) AS d
    UNION ALL SELECT DATEADD(day, 1, d) FROM Dates WHERE d < '2026-12-31'
)
INSERT INTO DimDate
SELECT CONVERT(INT, FORMAT(d, 'yyyyMMdd')), d, YEAR(d), DATEPART(quarter, d), MONTH(d), DATENAME(month, d),
       DAY(d), DATEPART(weekday, d), DATENAME(weekday, d), CASE WHEN DATEPART(weekday, d) IN (1, 7) THEN 1 ELSE 0 END,
       DATEPART(week, d),
       CASE WHEN MONTH(d) >= 7 THEN YEAR(d) + 1 ELSE YEAR(d) END,            -- fiscal year starts July
       CASE WHEN MONTH(d) >= 7 THEN DATEPART(quarter, d) - 2 ELSE DATEPART(quarter, d) + 2 END
FROM Dates OPTION (MAXRECURSION 400);
SELECT COUNT(*) AS Days, MIN(FullDate) AS FirstDay, MAX(FullDate) AS LastDay FROM DimDate;

What this query does

365 rows, 1 January to 31 December 2026. The recursive CTE (Day 6) starts at 1 January and adds one day until 31 December. SQL Server stops recursion after 100 levels by default, so OPTION (MAXRECURSION 400) allows a full year. FORMAT(d, 'yyyyMMdd') builds the integer key. Weekend uses weekday 1 (Sunday) and 7 (Saturday), which is correct for this server's default setting (DATEFIRST 7, us_english). This script is saved as its own file, dimdate.sql, because every warehouse needs one.

📍 Build it once with a script, keep the script, extend the years when needed.

#17

17. October 2026 in the new DimDate

SELECT * FROM DimDate WHERE Month = 10;

What this query does

31 rows. 1 October 2026 is a Thursday (DayOfWeek 5), the weekends are flagged, and October falls in fiscal year 2027, fiscal quarter 2, because this fiscal year starts in July (Pakistan's government fiscal year runs July to June).

📍 Every attribute a report could want, ready to filter and group by.

#18

18. Check the fiscal columns: the first day of each month

SELECT Month, MonthName, FiscalYear, FiscalQuarter FROM DimDate WHERE Day = 1 ORDER BY DateKey;

What this query does

January to June 2026 are fiscal year 2026, quarters 3 and 4; July to December are fiscal year 2027, quarters 1 and 2. The two CASE expressions are correct. Checking 12 rows by eye now saves a wrong fiscal report later.

📍 Test generated columns against cases you can work out by hand.

#19

19. Use it: rides by day, weekend flag and fiscal period

SELECT d.FullDate, d.DayName, d.IsWeekend, d.FiscalYear, d.FiscalQuarter, COUNT(*) AS Rides, SUM(f.FareAmount) AS Fare
FROM FactRide f JOIN DimDate d ON d.DateKey = f.DateKey
GROUP BY d.FullDate, d.DayName, d.IsWeekend, d.FiscalYear, d.FiscalQuarter;

What this query does

Three rides on Thursday 1 October (1,150) and two on Friday 2 October (880), both weekdays in fiscal 2027 Q2. FactRide's DateKey column was built on Day 17 for the small DimRideDate table, yet it joins to the new DimDate with no change, because both use the same yyyymmdd integer. No YEAR(), DATENAME() or fiscal-year logic appears in the query.

📍 The fact stores a date key; everything about the date comes from the dimension.

Surrogate keys: why the fact never stores the natural key

#20

20. Join on the natural key instead of the surrogate

USE AdventureWorksDW2022;
SELECT 'Surrogate key (ProductKey)' AS JoinedOn, COUNT(*) AS Lines, SUM(f.SalesAmount) AS Revenue
FROM FactResellerSales f JOIN DimProduct p ON p.ProductKey = f.ProductKey
WHERE p.ProductAlternateKey = 'FR-M94B-38'
UNION ALL
SELECT 'Natural key (ProductAlternateKey)', COUNT(*), SUM(f.SalesAmount)
FROM FactResellerSales f
JOIN DimProduct sold ON sold.ProductKey = f.ProductKey
JOIN DimProduct p    ON p.ProductAlternateKey = sold.ProductAlternateKey
WHERE p.ProductAlternateKey = 'FR-M94B-38';

What this query does

Through the surrogate key: 289 lines and 501,788.20, the true figures from drill 3. Through the natural key: 867 lines and 1,505,364.59, exactly three times too much, because the product code matches all three versions of the product and every sale is joined to each of them. Once a dimension keeps history, the natural key is no longer unique, so only the surrogate key can tell the fact which version it belongs to.

📍 Facts store surrogate keys only; the natural key stays in the dimension for lookups.

Columns added to the Type 2 dimension: DimRider now has EffectiveFrom, EffectiveTo and IsCurrent (step 6), and its uniqueness rule is "one current row per phone number" (step 8).

Pickup time: I chose PickupDateKey plus a PickupHour column, not a time-of-day dimension. FactRide already has DateKey (yyyymmdd, which joins to the new DimDate, step 19) and PickupHour (0 to 23). The questions the business asks are by hour ("morning peak", "late night"), so a 24-value column is enough. A DimTime with 1,440 rows (one per minute) would only pay off if reports grouped by named time bands that change, or by minute. The exact PickupTime and DropoffTime stay in the fact to calculate durations.

Self-test: answers

Type 1 vs Type 2 with the Ayesha example: Ayesha lived in Lahore and moved to Islamabad on 15 October. Type 1 would overwrite her city, so her rides on 1 October would suddenly appear under Islamabad and Lahore's October revenue would drop by 970 (step 12). Type 2 closes her Lahore row and adds an Islamabad row with a new key (6); old rides keep key 1 and stay in Lahore, new rides get key 6.

Why a fact table never stores the natural key: once a dimension keeps history, the natural key matches several rows, so a join on it multiplies the facts: three times too much revenue in step 20. Natural keys can also change, be reused, clash between source systems or be long strings.

Five columns a date dimension should have: DateKey (yyyymmdd), FullDate, Year, MonthName, DayName, plus Quarter, IsWeekend, FiscalYear, FiscalQuarter and a holiday flag.

Why DateKey is an integer like 20261030 and not a DATE: not to save space (DATE takes 3 bytes, INT 4). It is readable (you can see the date in the number), sorts in date order, joins like every other integer surrogate key, works well for partitioning by range, and can hold special members that are not dates, such as -1 for "unknown date" or 99991231 for "no end date", which a real DATE column cannot express as a row of its own.
