Day 22: ETL vs ELT, staging, full and incremental extract

Fri 13 November 2026 · 17 queries · run on AWPractice, reading AdventureWorks2022

Goal: copy source data into a staging area completely and provably, then copy only what changed.

Read: Microsoft Learn "Extract, transform, and load (ETL)" (the ETL vs ELT section); Kimball Group "The 34 subsystems of ETL" (subsystems 1 to 3: data profiling, change data capture, extract).

Set up the staging area

#1

1. Two new schemas: stg for raw copies, etl for bookkeeping

USE AWPractice;
IF SCHEMA_ID('stg') IS NULL EXEC('CREATE SCHEMA stg');   -- staging: raw copies of source tables
IF SCHEMA_ID('etl') IS NULL EXEC('CREATE SCHEMA etl');   -- load log and watermarks
SELECT name AS SchemaName, schema_id FROM sys.schemas WHERE name IN ('stg', 'etl', 'dw', 'reporting');

What this query does

CREATE SCHEMA must be the only statement in its batch, so it runs inside EXEC(), and the IF makes the script safe to run twice. stg (staging) will hold raw copies of the source tables, taken as they are, with no cleaning. etl will hold the bookkeeping: the load log and the watermarks. Next to the reporting schema from Day 10, AWPractice now has a separate place for each stage of the pipeline: raw (stg), the process (etl) and, from Day 24, the finished warehouse (dw).

📍 Keep raw copies, bookkeeping and finished tables in separate schemas.

#2

2. A load log: every extract writes one row

IF OBJECT_ID('etl.LoadLog') IS NULL
    CREATE TABLE etl.LoadLog (
        LogID        INT IDENTITY PRIMARY KEY,
        Step         VARCHAR(30)  NOT NULL,      -- 'Extract full', 'Extract incremental'
        TableName    VARCHAR(60)  NOT NULL,
        RowsAffected INT          NOT NULL,
        StartedAt    DATETIME2(3) NOT NULL,
        EndedAt      DATETIME2(3) NOT NULL
    );
SELECT * FROM etl.LoadLog;

What this query does

An empty table with one row per extract: which step ran, which table it filled, how many rows it moved and when it started and ended. LogID is an IDENTITY, so the log is in run order. The IF OBJECT_ID check means re-running the script keeps the history instead of wiping it. SSIS packages and stored procedures in real teams write to a table like this so that a failed or empty load is noticed the next morning, not at month end.

📍 If a load does not write down what it did, nobody can prove it ran.

Full extract: copy what the warehouse needs, nothing more

#3

3. Extract the order headers from AdventureWorks2022

DECLARE @t0 DATETIME2(3) = SYSDATETIME();
DROP TABLE IF EXISTS stg.SalesOrderHeader;
SELECT SalesOrderID, OrderDate, DueDate, ShipDate, Status, OnlineOrderFlag, CustomerID, SalesPersonID,
       TerritoryID, SubTotal, TaxAmt, Freight, TotalDue, ModifiedDate,
       SYSDATETIME() AS ExtractedAt                              -- when this copy was taken
INTO stg.SalesOrderHeader
FROM AdventureWorks2022.Sales.SalesOrderHeader;
DECLARE @n INT = @@ROWCOUNT;                                     -- read it immediately
INSERT INTO etl.LoadLog VALUES ('Extract full', 'stg.SalesOrderHeader', @n, @t0, SYSDATETIME());
SELECT * FROM etl.LoadLog WHERE LogID = SCOPE_IDENTITY();

What this query does

31,465 order headers copied from AdventureWorks2022 into stg.SalesOrderHeader in a fraction of a second. The three-part name AdventureWorks2022.Sales.SalesOrderHeader reads from another database on the same server. Only 14 of the 26 source columns are taken: the warehouse does not need rowguid, the credit-card ID or the comment. SELECT INTO creates the staging table with the source's column types and no keys or constraints, which is what staging should be: a fast, faithful copy. DROP TABLE IF EXISTS first makes the extract a full refresh that can be run any number of times. @@ROWCOUNT is read into @n on the very next line, because the next statement would reset it.

📍 Extract = a plain copy of the columns you need, stamped with when it was taken.

#4

4. Extract the order lines

DECLARE @t0 DATETIME2(3) = SYSDATETIME();
DROP TABLE IF EXISTS stg.SalesOrderDetail;
SELECT SalesOrderID, SalesOrderDetailID, ProductID, OrderQty, UnitPrice, UnitPriceDiscount, LineTotal, ModifiedDate,
       SYSDATETIME() AS ExtractedAt
INTO stg.SalesOrderDetail
FROM AdventureWorks2022.Sales.SalesOrderDetail;
DECLARE @n INT = @@ROWCOUNT;
INSERT INTO etl.LoadLog VALUES ('Extract full', 'stg.SalesOrderDetail', @n, @t0, SYSDATETIME());
SELECT * FROM etl.LoadLog WHERE LogID = SCOPE_IDENTITY();

What this query does

121,317 order lines in under a second. The pattern is identical to step 3: drop, copy the needed columns plus ExtractedAt, capture the row count, write a log row. Every extract in a pipeline should look the same so that anyone can read any of them.

📍 Each source table gets its own staging table and its own log row.

#5

5. Extract customers with their name and home city

DECLARE @t0 DATETIME2(3) = SYSDATETIME();
DROP TABLE IF EXISTS stg.Customer;
SELECT c.CustomerID, c.PersonID, c.StoreID, c.TerritoryID, p.FirstName, p.LastName,
       a.City, sp.CountryRegionCode, c.ModifiedDate, SYSDATETIME() AS ExtractedAt
INTO stg.Customer
FROM AdventureWorks2022.Sales.Customer c
LEFT JOIN AdventureWorks2022.Person.Person p ON p.BusinessEntityID = c.PersonID
LEFT JOIN AdventureWorks2022.Person.BusinessEntityAddress bea
       ON bea.BusinessEntityID = c.PersonID AND bea.AddressTypeID = 2          -- 2 = Home
LEFT JOIN AdventureWorks2022.Person.Address a        ON a.AddressID = bea.AddressID
LEFT JOIN AdventureWorks2022.Person.StateProvince sp ON sp.StateProvinceID = a.StateProvinceID;
DECLARE @n INT = @@ROWCOUNT;
INSERT INTO etl.LoadLog VALUES ('Extract full', 'stg.Customer', @n, @t0, SYSDATETIME());
SELECT * FROM etl.LoadLog WHERE LogID = SCOPE_IDENTITY();

What this query does

19,820 customers, one row per customer. A customer's name is in Person.Person and the home city is three tables further away (BusinessEntityAddress, Address, StateProvince), so this extract joins them. Every join is a LEFT JOIN: store customers have no person and no home address, and an INNER JOIN would silently drop them. The staging row count must equal the source count (19,820 = 19,820), which proves no customer was lost or duplicated. AddressTypeID = 2 picks the Home address only, so no customer gets two rows.

📍 LEFT JOINs in an extract: never lose a source row because a lookup is missing.

What this query does

508 products. This week's product source is AWPractice's own copy of Production.Product (made on Day 9, with four practice products added), not AdventureWorks2022 itself. Steps 11 to 14 need to change prices and add a product, and a sample database that other days depend on should never be edited. In a real job the source system is someone else's application; you only read from it.

📍 Pick a source you are allowed to change when you need to test change handling.

#7

7. Reconcile: does staging match the source?

SELECT 'SalesOrderHeader' AS TableName,
       (SELECT COUNT(*) FROM AdventureWorks2022.Sales.SalesOrderHeader) AS SourceRows,
       (SELECT COUNT(*) FROM stg.SalesOrderHeader) AS StagingRows,
       (SELECT SUM(TotalDue) FROM AdventureWorks2022.Sales.SalesOrderHeader) AS SourceTotal,
       (SELECT SUM(TotalDue) FROM stg.SalesOrderHeader) AS StagingTotal
UNION ALL
SELECT 'SalesOrderDetail', (SELECT COUNT(*) FROM AdventureWorks2022.Sales.SalesOrderDetail),
       (SELECT COUNT(*) FROM stg.SalesOrderDetail),
       (SELECT SUM(LineTotal) FROM AdventureWorks2022.Sales.SalesOrderDetail), (SELECT SUM(LineTotal) FROM stg.SalesOrderDetail)
UNION ALL
SELECT 'Customer', (SELECT COUNT(*) FROM AdventureWorks2022.Sales.Customer), (SELECT COUNT(*) FROM stg.Customer), NULL, NULL
UNION ALL
SELECT 'Product', (SELECT COUNT(*) FROM dbo.Product), (SELECT COUNT(*) FROM stg.Product),
       (SELECT SUM(ListPrice) FROM dbo.Product), (SELECT SUM(ListPrice) FROM stg.Product);

What this query does

Every staging table has exactly as many rows as its source, and the money totals match to the last decimal: 123,216,786.1159 for TotalDue and 109,846,381.3999 for LineTotal. A matching count alone could hide a fault (one row lost and another duplicated), and a matching total alone could hide another, so check both. Customer has no money column, so only the count is compared. This check is the extract's proof of completeness; Day 25 turns checks like this into an automatic test suite.

📍 Check two things after every extract: the row count and the total of a money column.

#8

8. Read the log

SELECT LogID, Step, TableName, RowsAffected, StartedAt, EndedAt,
       DATEDIFF(millisecond, StartedAt, EndedAt) AS Ms
FROM etl.LoadLog ORDER BY LogID;

What this query does

Four log rows, one per extract: 31,465, 121,317, 19,820 and 508 rows, each finishing in under a second (9 to 958 milliseconds in this run). DATEDIFF(millisecond, ...) works out each duration. If tomorrow's run logs 0 order lines, or takes 40 seconds instead of one, the log shows it without anyone opening the data.

📍 The log answers "did it run, how much did it move, how long did it take".

Incremental extract: only what changed since last time

#9

9. A watermark table, set to where the full extract finished

IF OBJECT_ID('etl.Watermark') IS NULL
    CREATE TABLE etl.Watermark (TableName VARCHAR(60) PRIMARY KEY, LastModified DATETIME NOT NULL);
DELETE FROM etl.Watermark WHERE TableName = 'dbo.Product';
INSERT INTO etl.Watermark SELECT 'dbo.Product', MAX(ModifiedDate) FROM stg.Product;
SELECT * FROM etl.Watermark;

What this query does

A watermark is a bookmark: the newest ModifiedDate that has already been copied. The full extract in step 6 copied everything up to 16 October 2026, 17:51:46 (when the practice products were last edited on Day 9), so that becomes the starting watermark for dbo.Product. The table has one row per source table, so the same design works for any number of tables.

📍 The watermark is the newest ModifiedDate already copied.

#10

10. What has changed since the watermark?

SELECT p.ProductID, p.Name, p.ListPrice, p.ModifiedDate
FROM dbo.Product p
WHERE p.ModifiedDate > (SELECT LastModified FROM etl.Watermark WHERE TableName = 'dbo.Product');

What this query does

Zero rows. No product has a ModifiedDate later than the watermark, because nothing has changed since the full extract. An incremental extract asks only this question: which rows were modified after the last one I copied?

📍 Right after a full extract, nothing is newer than the watermark.

#11

11. The source system changes: two new prices and one new product

UPDATE dbo.Product SET ListPrice = 1499.00, ModifiedDate = '2026-11-13 09:00' WHERE ProductID = 680;
UPDATE dbo.Product SET ListPrice = 6.49,    ModifiedDate = '2026-11-13 09:00' WHERE ProductID = 1001;
IF NOT EXISTS (SELECT 1 FROM dbo.Product WHERE ProductNumber = 'PR-1005')
    INSERT INTO dbo.Product (Name, ProductNumber, MakeFlag, FinishedGoodsFlag, SafetyStockLevel, ReorderPoint,
                             StandardCost, ListPrice, DaysToManufacture, SellStartDate, rowguid, ModifiedDate)
    VALUES ('Practice Light', 'PR-1005', 0, 1, 4, 3, 7.50, 17.99, 0, '2026-11-13', NEWID(), '2026-11-13 09:00');
SELECT ProductID, Name, ListPrice, ModifiedDate FROM dbo.Product WHERE ModifiedDate >= '2026-11-13';

What this query does

The source system changes, as it would during a working day. The HL Road Frame (ProductID 680) goes from 1,431.50 to 1,499.00, the Practice Bottle (1001) from 5.99 to 6.49, and a new product, the Practice Light, is added with ProductID 1005 at 17.99. Each change sets ModifiedDate to 13 November 2026, 09:00. The IF NOT EXISTS stops a second run from adding the light twice. These are the changes the incremental extract must catch, and on Day 24 the price changes will become Type 2 history in the product dimension.

📍 A well-behaved source updates ModifiedDate on every change. Incremental extract depends on it.

#12

12. Ask again: what has changed?

SELECT p.ProductID, p.Name, p.ListPrice, p.ModifiedDate
FROM dbo.Product p
WHERE p.ModifiedDate > (SELECT LastModified FROM etl.Watermark WHERE TableName = 'dbo.Product');

What this query does

Now the same query from step 10 returns three rows: the two re-priced products and the new one. Updates and inserts are caught the same way, because both set ModifiedDate. What this method cannot catch is a deleted row (it is no longer there to have a date) or a change made by a program that forgets to update ModifiedDate. Real pipelines handle deletes with a periodic full comparison or with SQL Server's Change Data Capture.

📍 Same query, new answer: exactly the rows the source touched.

#13

13. The incremental extract: copy the changes, then move the watermark

DECLARE @t0 DATETIME2(3) = SYSDATETIME();
DECLARE @wm DATETIME = (SELECT LastModified FROM etl.Watermark WHERE TableName = 'dbo.Product');
DROP TABLE IF EXISTS stg.ProductDelta;
SELECT ProductID, Name, ProductNumber, Color, StandardCost, ListPrice, ProductSubcategoryID, ModifiedDate,
       SYSDATETIME() AS ExtractedAt
INTO stg.ProductDelta
FROM dbo.Product WHERE ModifiedDate > @wm;
DECLARE @n INT = @@ROWCOUNT;
UPDATE etl.Watermark SET LastModified = ISNULL((SELECT MAX(ModifiedDate) FROM stg.ProductDelta), @wm)
WHERE TableName = 'dbo.Product';
INSERT INTO etl.LoadLog VALUES ('Extract incremental', 'stg.ProductDelta', @n, @t0, SYSDATETIME());
SELECT @wm AS OldWatermark, (SELECT LastModified FROM etl.Watermark WHERE TableName = 'dbo.Product') AS NewWatermark,
       @n AS RowsExtracted;

What this query does

The incremental extract copies only the changed rows into stg.ProductDelta: 3 rows instead of 508. It then moves the watermark from 16 October 17:51:46 to 13 November 09:00, the newest ModifiedDate it just copied, and writes a log row. The watermark is set from the copied data (MAX of ModifiedDate in the delta), not from the clock, so a change made while the extract was running is not skipped. ISNULL keeps the old watermark when nothing was copied.

📍 Copy the changed rows and move the watermark in the same run.

#14

14. Run exactly the same extract again

DECLARE @t0 DATETIME2(3) = SYSDATETIME();
DECLARE @wm DATETIME = (SELECT LastModified FROM etl.Watermark WHERE TableName = 'dbo.Product');
DROP TABLE IF EXISTS stg.ProductDelta;
SELECT ProductID, Name, ProductNumber, Color, StandardCost, ListPrice, ProductSubcategoryID, ModifiedDate,
       SYSDATETIME() AS ExtractedAt
INTO stg.ProductDelta
FROM dbo.Product WHERE ModifiedDate > @wm;
DECLARE @n INT = @@ROWCOUNT;
UPDATE etl.Watermark SET LastModified = ISNULL((SELECT MAX(ModifiedDate) FROM stg.ProductDelta), @wm)
WHERE TableName = 'dbo.Product';
INSERT INTO etl.LoadLog VALUES ('Extract incremental', 'stg.ProductDelta', @n, @t0, SYSDATETIME());
SELECT @wm AS OldWatermark, (SELECT LastModified FROM etl.Watermark WHERE TableName = 'dbo.Product') AS NewWatermark,
       @n AS RowsExtracted;

What this query does

The identical script, run a second time, extracts 0 rows and leaves the watermark at 13 November 09:00. The changes were already copied and the watermark has moved past them. This is what makes an incremental extract safe to schedule every hour: running it again never copies the same change twice.

📍 An incremental extract run twice copies nothing the second time: safe to re-run.

#15

15. Full vs incremental in the log

SELECT LogID, Step, TableName, RowsAffected, DATEDIFF(millisecond, StartedAt, EndedAt) AS Ms
FROM etl.LoadLog ORDER BY LogID;

What this query does

The log now tells the whole story: four full extracts (31,465, 121,317, 19,820 and 508 rows), then two incremental runs on products, with 3 rows and then 0. On a database with millions of rows, the difference between copying everything and copying only the changes is the difference between a load that takes hours and one that takes seconds.

📍 Full extracts move everything; incremental ones move only what changed.

#16

16. Profile the order headers

SELECT COUNT(*) AS Orders, COUNT(DISTINCT CustomerID) AS Customers,
       SUM(CASE WHEN SalesPersonID IS NULL THEN 1 ELSE 0 END) AS NoSalesPerson,
       SUM(CASE WHEN OnlineOrderFlag = 1 THEN 1 ELSE 0 END) AS OnlineOrders,
       SUM(CASE WHEN ShipDate IS NULL THEN 1 ELSE 0 END) AS NotShipped,
       MIN(OrderDate) AS FirstOrder, MAX(OrderDate) AS LastOrder
FROM stg.SalesOrderHeader;

What this query does

31,465 orders from 19,119 different customers, placed between 31 May 2011 and 30 June 2014. 27,659 orders have no SalesPersonID, and exactly 27,659 are online orders: the NULL is not missing data, it means the customer bought online with no sales rep. The transform step must turn that NULL into a readable label, not drop or guess it. No order lacks a ShipDate. Every number here becomes a rule or a check later.

📍 Profiling = counting NULLs, ranges and distinct values before you trust the data.

17. Profile the customers: what is missing?

SELECT COUNT(*) AS Customers,
       SUM(CASE WHEN PersonID IS NULL THEN 1 ELSE 0 END)  AS NoPerson,
       SUM(CASE WHEN StoreID  IS NULL THEN 1 ELSE 0 END)  AS NoStore,
       SUM(CASE WHEN FirstName IS NULL THEN 1 ELSE 0 END) AS NoName,
       SUM(CASE WHEN City IS NULL THEN 1 ELSE 0 END)      AS NoCity,
       COUNT(DISTINCT City) AS Cities, COUNT(DISTINCT CountryRegionCode) AS Countries

What this query does

19,820 customers. 701 have no PersonID and therefore no name: they are stores, not people. 18,484 have no StoreID: they are individual online shoppers. 1,336 have no city, and a follow-up check showed that these are exactly the 1,336 store customers (701 stores with no contact person, and 635 that also have a contact person). A store's address is recorded against the store, not the contact, and every individual customer has a home city. The data covers 269 cities in 6 countries. 📍 Write down every gap now; each one needs a rule in the transform step.

Self-test: answers

ETL vs ELT in one sentence each: ETL transforms the data in a separate tool before loading it; ELT loads raw data into the warehouse first and transforms it there with SQL. On SQL Server, both are common: SSIS for ETL, stored procedures over staging tables for ELT.

Why staging tables have no keys or constraints: their job is to receive whatever the source sends, quickly and completely. A constraint would make the extract fail on the very rows that need attention. The checks belong in the transform and validation steps, where a bad row can be reported instead of stopping the whole load.

Why the watermark is set from the data and not from the clock: if it were set to "now" at the end of the run, any row changed while the extract was running would carry a ModifiedDate earlier than the new watermark and would never be copied. MAX(ModifiedDate) of the copied rows can only be as new as what was actually copied.

What a ModifiedDate watermark misses: deleted rows, and changes made without updating ModifiedDate. Fixes: a periodic full extract compared with the warehouse, a "deleted" flag in the source, or Change Data Capture / change tracking in SQL Server.

Full or incremental for each table here: products, customers and order headers change, so in a real pipeline all three would be incremental; Product was done incrementally today as the example. Small reference tables (territories, categories) are cheaper to copy in full every time.
