Day 23: Transform: cleaning and standardising

Mon 16 November 2026 · 19 queries · run on AWPractice

Goal: turn raw staged data into consistent, typed, de-duplicated rows, and account for every row that could not be used.

Read: Microsoft Learn "TRY_CONVERT", "TRIM", "CREATE VIEW"; Kimball Group "The 34 subsystems of ETL" (subsystem 4, data cleansing, and 8, error event handling).

The T in ELT: Day 22 copied the data as it was. Today decides what it should look like in the warehouse: no NULLs in columns people group by, one spelling per city, one format per phone number, real dates and numbers instead of text, one row per real person. Two sources are cleaned. AdventureWorks is already tidy, so its rules are short and written as views that Day 24 will load from. The second source is deliberately messy: twelve web sign-ups typed by real people, the kind of file every data team receives.

1. Three more small full extracts: stores, subcategories, categories

USE AWPractice;
DECLARE @t0 DATETIME2(3) = SYSDATETIME(), @n INT;
DROP TABLE IF EXISTS stg.Store, stg.ProductSubcategory, stg.ProductCategory;
SELECT s.BusinessEntityID AS StoreID, s.Name AS StoreName, a.City, sp.CountryRegionCode, SYSDATETIME() AS ExtractedAt
INTO stg.Store
FROM AdventureWorks2022.Sales.Store s
LEFT JOIN AdventureWorks2022.Person.BusinessEntityAddress bea
       ON bea.BusinessEntityID = s.BusinessEntityID AND bea.AddressTypeID = 3     -- 3 = Main Office
LEFT JOIN AdventureWorks2022.Person.Address a        ON a.AddressID = bea.AddressID
LEFT JOIN AdventureWorks2022.Person.StateProvince sp ON sp.StateProvinceID = a.StateProvinceID;
SET @n = @@ROWCOUNT; INSERT INTO etl.LoadLog VALUES ('Extract full', 'stg.Store', @n, @t0, SYSDATETIME());
SELECT ProductSubcategoryID, ProductCategoryID, Name INTO stg.ProductSubcategory FROM AdventureWorks2022.Production.ProductSubcategory;
SET @n = @@ROWCOUNT; INSERT INTO etl.LoadLog VALUES ('Extract full', 'stg.ProductSubcategory', @n, @t0, SYSDATETIME());

SELECT LogID, Step, TableName, RowsAffected FROM etl.LoadLog WHERE LogID > 6;

What this query does

Three lookup tables the transform rules need, extracted in full with the Day 22 pattern: 701 stores (with the city and country of each store's main office, AddressTypeID 3), 37 product subcategories and 4 categories. 📍 Lookups (stores, categories) are small: extract them in full every time.

Transform rules on the real data, written as views

#2

2. The customer rules: type, name, city and country with no NULLs

CREATE OR ALTER VIEW etl.vCustomer AS
SELECT c.CustomerID,
       CASE WHEN c.PersonID IS NULL THEN 'Store'
            WHEN c.StoreID  IS NULL THEN 'Individual'
            ELSE 'Store contact' END                                   AS CustomerType,
       COALESCE(c.FirstName + ' ' + c.LastName, s.StoreName)          AS CustomerName,
       ISNULL(s.StoreName, 'No store')                                 AS StoreName,
       COALESCE(c.City, s.City, 'Unknown')                             AS City,
       CASE COALESCE(c.CountryRegionCode, s.CountryRegionCode)
            WHEN 'US' THEN 'United States' WHEN 'CA' THEN 'Canada'  WHEN 'GB' THEN 'United Kingdom'
            WHEN 'FR' THEN 'France'        WHEN 'DE' THEN 'Germany' WHEN 'AU' THEN 'Australia'
            ELSE 'Unknown' END                                         AS Country,
       c.ModifiedDate
FROM stg.Customer c
LEFT JOIN stg.Store s ON s.StoreID = c.StoreID;
GO
SELECT TOP 6 * FROM etl.vCustomer ORDER BY CustomerID;

What this query does

The transform for customers, written as a view in the etl schema. CREATE OR ALTER makes it re-runnable, and GO ends the batch because CREATE VIEW must be alone in its batch. The rules: CustomerType says what kind of customer each row is (Store, Individual or Store contact) instead of leaving a NULL PersonID to be interpreted; CustomerName takes the person's name, or the store's name for stores; City and Country take the person's home address, or else the store's main office, or else 'Unknown'; the two-letter country code becomes a readable name. The first six customers are all stores, so their name and city come from stg.Store. No data is copied: the view runs the rules whenever it is read, and Day 24 will load the warehouse from it.

📍 A view is a transform you can read, test and rerun: no data is copied until the load.

3. Did the rules close the gaps found on Day 22?

FROM etl.vCustomer GROUP BY CustomerType;

What this query does

Day 22 found 701 customers with no name and 1,336 with no city. Through the view, every one of the 19,820 customers has a name, a city and a country: 701 stores, 635 store contacts and 18,484 individual customers. The 1,336 cities were not invented or set to 'Unknown': they came from the store's own main-office address, which is a real answer. 'Unknown' is still in the rule, as a safety net for future rows.

📍 Measure a rule after writing it: the gap should be gone, not just renamed.

#4

4. The product rules: no NULL colour, category names, a price band

CREATE OR ALTER VIEW etl.vProduct AS
SELECT p.ProductID, p.ProductNumber, p.Name AS ProductName,
       ISNULL(p.Color, 'No colour')        AS Colour,
       ISNULL(sc.Name, 'Not for sale')     AS Subcategory,
       ISNULL(cat.Name, 'Not for sale')    AS Category,
       p.StandardCost, p.ListPrice,
       CASE WHEN p.ListPrice = 0    THEN 'No list price'
            WHEN p.ListPrice < 50   THEN 'Under 50'
            WHEN p.ListPrice < 500  THEN '50 to 499'
            WHEN p.ListPrice < 1500 THEN '500 to 1,499'
            ELSE '1,500 and over' END     AS PriceBand,
       p.ModifiedDate
FROM stg.Product p
LEFT JOIN stg.ProductSubcategory sc ON sc.ProductSubcategoryID = p.ProductSubcategoryID
LEFT JOIN stg.ProductCategory cat   ON cat.ProductCategoryID   = sc.ProductCategoryID;
GO
SELECT Category, PriceBand, COUNT(*) AS Products FROM etl.vProduct GROUP BY Category, PriceBand ORDER BY Category, MIN(ListPrice);

What this query does

The product transform: a NULL colour becomes 'No colour', the subcategory and category IDs become names through two LEFT JOINs, and a price band is derived from ListPrice. 213 products have no subcategory and show as 'Not for sale': 200 of them have no list price at all (they are parts used to build bikes, not sold on their own). Bikes are all 500 or more; clothing and accessories are almost all under 500. Defining the bands here means every report and every analyst uses the same boundaries.

📍 Derived columns (a band, a label) belong in the transform, so every report uses the same definition.

#5

5. The sales-line rules: one row per order line, ready for the fact

CREATE OR ALTER VIEW etl.vSalesLine AS
SELECT d.SalesOrderID, d.SalesOrderDetailID,
       YEAR(h.OrderDate) * 10000 + MONTH(h.OrderDate) * 100 + DAY(h.OrderDate) AS OrderDateKey,   -- yyyymmdd
       h.CustomerID, d.ProductID, h.TerritoryID,
       CASE h.OnlineOrderFlag WHEN 1 THEN 'Online' ELSE 'Reseller' END        AS SalesChannel,
       h.SalesPersonID,                                                        -- NULL = online, mapped on Day 24
       d.OrderQty AS Quantity, d.UnitPrice, d.UnitPriceDiscount,
       CAST(d.LineTotal AS DECIMAL(19, 4))                                     AS SalesAmount
FROM stg.SalesOrderDetail d
JOIN stg.SalesOrderHeader h ON h.SalesOrderID = d.SalesOrderID;
GO
SELECT SalesChannel, COUNT(*) AS Lines, COUNT(DISTINCT SalesOrderID) AS Orders, SUM(SalesAmount) AS Revenue
FROM etl.vSalesLine GROUP BY SalesChannel;

What this query does

One row per order line, with the order's date, customer, territory and channel brought down from the header. OrderDateKey is the yyyymmdd integer that joins to a date dimension (Day 20). OnlineOrderFlag becomes a word, 'Online' or 'Reseller'. 121,317 lines in total (60,398 online, 60,919 reseller) from 31,465 orders, the same as the extract. The money check found something: Online 29,358,677.2207 plus Reseller 80,487,704.2043 is 109,846,381.4250, while the extracted LineTotal adds up to 109,846,381.3999. LineTotal is stored with 6 decimals; casting each line to DECIMAL(19,4) rounds it, and 121,317 small roundings add up to 2.5 cents. That is acceptable for a sales report, but it has to be a decision, written down, not a surprise found later. Online revenue matches FactInternetSales exactly (Day 15).

📍 The transform must not create or lose money: check the total against the extract.

#6

6. Building a date key: FORMAT is easy to read and slow

DECLARE @t DATETIME2(3), @k INT, @a INT, @b INT;
SET @t = SYSDATETIME();
SELECT @k = MAX(CONVERT(INT, FORMAT(h.OrderDate, 'yyyyMMdd')))
FROM stg.SalesOrderDetail d JOIN stg.SalesOrderHeader h ON h.SalesOrderID = d.SalesOrderID;
SET @a = DATEDIFF(millisecond, @t, SYSDATETIME());
SET @t = SYSDATETIME();
SELECT @k = MAX(YEAR(h.OrderDate) * 10000 + MONTH(h.OrderDate) * 100 + DAY(h.OrderDate))
FROM stg.SalesOrderDetail d JOIN stg.SalesOrderHeader h ON h.SalesOrderID = d.SalesOrderID;
SET @b = DATEDIFF(millisecond, @t, SYSDATETIME());
SELECT @a AS FormatMs, @b AS ArithmeticMs, @k AS LastDateKey;

What this query does

Two ways to build the same date key for all 121,317 lines, timed with SYSDATETIME before and after each. FORMAT(OrderDate, 'yyyyMMdd') is the easiest to read but calls the .NET formatting library once per row; YEAR() * 10000 + MONTH() * 100 + DAY() is plain integer arithmetic. Both give the same last key, 20140630. In the run shown, FORMAT took 513 milliseconds and the arithmetic 180: almost three times as long for the same answer (the exact figures vary from run to run). On a fact load with millions of rows, that difference is minutes. This is why the view in step 5 uses the arithmetic version.

📍 FORMAT() runs .NET code on every row; plain arithmetic does the same job far faster.

8. Profile the mess

SELECT COUNT(*) AS Rows,
       COUNT(DISTINCT LOWER(TRIM(Email))) AS DistinctEmails,
       SUM(CASE WHEN TRIM(Email) = '' THEN 1 ELSE 0 END) AS BlankEmails,
       COUNT(DISTINCT City) AS CitySpellings,
       SUM(CASE WHEN TRY_CONVERT(DATE, SignupDate, 23) IS NULL THEN 1 ELSE 0 END) AS NotIsoDates,
       SUM(CASE WHEN TRY_CAST(FirstOrderAmount AS DECIMAL(10,2)) IS NULL THEN 1 ELSE 0 END) AS NotNumbers
FROM stg.WebSignupRaw;

What this query does

The profile before any cleaning. 12 rows but only 10 distinct emails (after lower-casing and trimming), so two people are duplicated; the blank email counts as one of the 10. 9 different city spellings for 5 real cities: the server's collation ignores case and trailing spaces, so 'lahore' and 'Lahore' already count as one, but ' Islamabad' with a leading space does not. 4 dates are not in ISO form (yyyy-mm-dd) and 5 amounts are not plain numbers. #9

9. Convert the dates the strict way: CONVERT stops at the first bad value

SELECT SignupID, SignupDate, CONVERT(DATE, SignupDate, 23) AS AsDate FROM stg.WebSignupRaw;

What this query does

CONVERT with style 23 (yyyy-mm-dd) cannot read '02/11/2026' in row 2, and the whole statement fails with 'Conversion failed' (Msg 241): not one row is returned, not even the ones that were fine. In a load procedure, one badly typed date in a file of a million rows would stop the load and nothing would be loaded. The error is expected; it is the reason for the next step.

📍 CONVERT fails the whole query on one bad row. In a load, that is the whole night's run.

#10

10. TRY_CONVERT, one format at a time

SELECT SignupID, SignupDate,
       TRY_CONVERT(DATE, SignupDate, 23)  AS Iso_yyyy_mm_dd,
       TRY_CONVERT(DATE, SignupDate, 103) AS British_dd_mm_yyyy,
       TRY_CONVERT(DATE, SignupDate, 105) AS Italian_dd_mm_yyyy,
       TRY_CONVERT(DATE, SignupDate, 106) AS dd_mon_yyyy,
       COALESCE(TRY_CONVERT(DATE, SignupDate, 23),  TRY_CONVERT(DATE, SignupDate, 103),
                TRY_CONVERT(DATE, SignupDate, 105), TRY_CONVERT(DATE, SignupDate, 106)) AS CleanDate
FROM stg.WebSignupRaw;

What this query does

TRY_CONVERT returns NULL instead of failing, so each format can be tried in turn: 23 (ISO), 103 (British dd/mm/yyyy), 105 (Italian dd-mm-yyyy) and 106 (dd mon yyyy). COALESCE takes the first one that works. 11 of 12 dates are recovered; '2026-13-45' fits no format and stays NULL. Two things to notice. First, the style numbers are hints, not strict patterns: '3 Nov 2026' is accepted under every style. Second, '02/11/2026' is read as 2 November because styles 103 and 105 are day-first. Style 101 (US, month-first) would have read it as 11 February. The source is a Pakistani website, so day-first is the right rule, and that choice belongs in the documentation.

📍 Try each format the source is known to use; anything that fits none stays NULL and is flagged.

#11

11. Names: trim, collapse spaces, capitalise each word

SELECT SignupID, FullName AS Raw,
       UPPER(LEFT(f.First, 1)) + LOWER(SUBSTRING(f.First, 2, 50)) + ' ' +
       UPPER(LEFT(f.Last, 1))  + LOWER(SUBSTRING(f.Last, 2, 50))  AS CleanName
FROM stg.WebSignupRaw
CROSS APPLY (SELECT LTRIM(RTRIM(REPLACE(FullName, '  ', ' '))) AS n) t
CROSS APPLY (SELECT LEFT(t.n, CHARINDEX(' ', t.n + ' ') - 1) AS First,
                    LTRIM(SUBSTRING(t.n, CHARINDEX(' ', t.n + ' ') + 1, 50)) AS Last) f;

What this query does

The first CROSS APPLY trims the name and replaces double spaces with single ones; the second splits it at the first space into First and Last. Each part is then rebuilt with the first letter in upper case and the rest in lower case. ' ayesha KHAN ' and 'AYESHA KHAN' both become 'Ayesha Khan', and 'bilal ahmed' becomes 'Bilal Ahmed'. This simple rule would get names like 'McDonald' or 'van der Berg' wrong, which is acceptable for this source but worth knowing.

📍 CROSS APPLY gives a computed value a name, so the next step can use it.

#12

12. Emails: lower case, no spaces, and a basic validity test

SELECT SignupID, Email AS Raw, e.Clean,
       CASE WHEN e.Clean = '' THEN 'Blank'
            WHEN e.Clean LIKE '% %' THEN 'Contains a space'
            WHEN e.Clean NOT LIKE '_%@_%._%' THEN 'No domain ending'
            ELSE 'OK' END AS EmailCheck
FROM stg.WebSignupRaw
CROSS APPLY (SELECT LOWER(TRIM(Email)) AS Clean) e;

What this query does

TRIM removes the space after 'Ayesha.Khan@Gmail.com ' and LOWER makes 'SARA.MALIK@HOTMAIL.COM' readable and comparable. Email addresses are not case-sensitive in practice, so lower case is safe. Three emails cannot be fixed by rules: row 4 has no domain ending ('@gmail' with no '.com'), row 5 is blank and row 8 has a space inside it ('fatima noor@gmail.com'). Guessing a fix (adding '.com', removing the space) could send a customer's data to a stranger, so they are flagged, not repaired. The LIKE pattern '_%@_%._%' means: at least one character, an @, at least one character, a dot, at least one character.

📍 Clean what can be cleaned (case, spaces at the ends); flag what cannot (a space inside).

#13

13. Phones: keep the digits, turn +92 into 0, check the length, format one way

SELECT SignupID, Phone AS Raw, d.Digits,
       CASE WHEN LEN(d.Digits) = 11 AND LEFT(d.Digits, 2) = '03'
            THEN LEFT(d.Digits, 4) + '-' + RIGHT(d.Digits, 7) END AS CleanPhone
FROM stg.WebSignupRaw
CROSS APPLY (SELECT REPLACE(REPLACE(REPLACE(REPLACE(Phone, '+', ''), '-', ''), ' ', ''), '(', '') AS s) x
CROSS APPLY (SELECT CASE WHEN LEFT(x.s, 2) = '92' AND LEN(x.s) = 12 THEN '0' + SUBSTRING(x.s, 3, 10) ELSE x.s END AS Digits) d;

What this query does

Nested REPLACEs strip '+', '-', spaces and brackets, leaving only digits. A number starting with 92 and 12 digits long is an international form ('+92 301 2222222'), so 92 is replaced by 0. A valid Pakistani mobile number is then 11 digits starting with 03, and is stored in one format, 0300-1234567. Five different spellings of numbers become one format, and both of Bilal's rows now show the same number (0301-2222222). Row 4 has only 10 digits ('0333-444444'), so it gets no clean phone.

📍 Store one format. Five ways of writing the same number make it five different customers.

#14

14. Cities: a mapping table for known spellings

DROP TABLE IF EXISTS etl.CityMap;
CREATE TABLE etl.CityMap (Variant NVARCHAR(50) PRIMARY KEY, City NVARCHAR(50) NOT NULL);
INSERT INTO etl.CityMap VALUES
 ('lahore', 'Lahore'), ('lhr', 'Lahore'), ('lahor', 'Lahore'),
 ('islamabad', 'Islamabad'), ('isb', 'Islamabad'),
 ('karachi', 'Karachi'), ('khi', 'Karachi'),
 ('rawalpindi', 'Rawalpindi'), ('rwp', 'Rawalpindi');
SELECT r.SignupID, r.City AS Raw, ISNULL(m.City, 'Unknown') AS CleanCity
FROM stg.WebSignupRaw r
LEFT JOIN etl.CityMap m ON m.Variant = LOWER(TRIM(r.City));

What this query does

A small table, etl.CityMap, lists every known spelling (in lower case) and the city it means. The raw city is trimmed and lower-cased, then looked up: 'LHR', 'Lahor' and 'lahore' all become Lahore, 'RWP' becomes Rawalpindi. The text 'NULL' in row 7 matches nothing and becomes 'Unknown'. When a new spelling turns up next month, someone adds a row to CityMap; nobody has to change the code. The LEFT JOIN keeps rows with unknown spellings instead of dropping them.

📍 A mapping table is data, not code: the business can add a spelling without a code change.

#15

15. Amounts: strip commas and "Rs", then TRY_CAST

SELECT SignupID, FirstOrderAmount AS Raw,
       TRY_CAST(TRIM(REPLACE(REPLACE(FirstOrderAmount, ',', ''), 'Rs', '')) AS DECIMAL(10, 2)) AS CleanAmount,
       CASE WHEN NULLIF(TRIM(FirstOrderAmount), '') IS NULL THEN 'Blank'
            WHEN TRY_CAST(TRIM(REPLACE(REPLACE(FirstOrderAmount, ',', ''), 'Rs', '')) AS DECIMAL(10, 2)) IS NULL THEN 'Not a number'
            ELSE 'OK' END AS AmountCheck
FROM stg.WebSignupRaw;

What this query does

Commas and 'Rs' are removed, the result is trimmed and TRY_CAST turns it into a DECIMAL. '1,200' becomes 1200.00, 'Rs 850' becomes 850.00 and '1,500.50' becomes 1500.50. Two amounts cannot be read, and they are different problems: row 5 is blank (the customer did not order) and row 7 is 'abc' (someone typed rubbish). A report might treat blank as zero, but 'abc' needs checking at the source. Row 10's '0' is a real value and stays 0.00.

📍 Blank and "not a number" are different problems; label them differently.

Put the rules together: clean, reject, de-duplicate

#16

16. Rejects go to their own table, with the reason

DROP TABLE IF EXISTS stg.WebSignupReject;
WITH Cleaned AS (
    SELECT CAST(r.SignupID AS INT) AS SignupID,
           UPPER(LEFT(f.First, 1)) + LOWER(SUBSTRING(f.First, 2, 50)) + ' ' +
           UPPER(LEFT(f.Last, 1))  + LOWER(SUBSTRING(f.Last, 2, 50))  AS FullName,
           LOWER(TRIM(r.Email)) AS Email,
           CASE WHEN LEN(d.Digits) = 11 AND LEFT(d.Digits, 2) = '03' THEN LEFT(d.Digits, 4) + '-' + RIGHT(d.Digits, 7) END AS Phone,
           ISNULL(m.City, 'Unknown') AS City,
           COALESCE(TRY_CONVERT(DATE, r.SignupDate, 23),  TRY_CONVERT(DATE, r.SignupDate, 103),
                    TRY_CONVERT(DATE, r.SignupDate, 105), TRY_CONVERT(DATE, r.SignupDate, 106)) AS SignupDate,
           TRY_CAST(TRIM(REPLACE(REPLACE(r.FirstOrderAmount, ',', ''), 'Rs', '')) AS DECIMAL(10, 2)) AS FirstOrderAmount
    FROM stg.WebSignupRaw r
    CROSS APPLY (SELECT LTRIM(RTRIM(REPLACE(r.FullName, '  ', ' '))) AS n) t
    CROSS APPLY (SELECT LEFT(t.n, CHARINDEX(' ', t.n + ' ') - 1) AS First, LTRIM(SUBSTRING(t.n, CHARINDEX(' ', t.n + ' ') + 1, 50)) AS Last) f
    CROSS APPLY (SELECT REPLACE(REPLACE(REPLACE(r.Phone, '+', ''), '-', ''), ' ', '') AS s) x
    CROSS APPLY (SELECT CASE WHEN LEFT(x.s, 2) = '92' AND LEN(x.s) = 12 THEN '0' + SUBSTRING(x.s, 3, 10) ELSE x.s END AS Digits) d
    LEFT JOIN etl.CityMap m ON m.Variant = LOWER(TRIM(r.City))
), Checked AS (
    SELECT *, CASE WHEN Email = '' THEN 'Blank email'
                   WHEN Email LIKE '% %' OR Email NOT LIKE '_%@_%._%' THEN 'Invalid email'
                   WHEN Phone IS NULL THEN 'Invalid phone' END AS RejectReason
    FROM Cleaned
)
SELECT r.*, c.RejectReason, SYSDATETIME() AS RejectedAt
INTO stg.WebSignupReject
FROM Checked c JOIN stg.WebSignupRaw r ON CAST(r.SignupID AS INT) = c.SignupID
WHERE c.RejectReason IS NOT NULL;
SELECT SignupID, FullName, Email, Phone, RejectReason FROM stg.WebSignupReject;

What this query does

All the rules from steps 10 to 15 combined in one CTE (Cleaned), then a second CTE (Checked) decides whether each row can be used. Three rows fail: Usman (email has no domain ending; his phone is also too short, but the first reason found is reported), Hina (blank email) and Fatima (space in the email). They are copied into stg.WebSignupReject with their original raw values and the reason, by joining back to the raw table on SignupID. Nothing is thrown away: the reject table is the to-do list for whoever owns the website.

📍 Never drop a bad row silently: park it with a reason so someone can fix the source.

#17

17. The clean table: valid rows only, one row per email, newest sign-up wins

DROP TABLE IF EXISTS stg.WebSignupClean;
WITH Cleaned AS (
    SELECT CAST(r.SignupID AS INT) AS SignupID,
           UPPER(LEFT(f.First, 1)) + LOWER(SUBSTRING(f.First, 2, 50)) + ' ' +
           UPPER(LEFT(f.Last, 1))  + LOWER(SUBSTRING(f.Last, 2, 50))  AS FullName,
           LOWER(TRIM(r.Email)) AS Email,
           CASE WHEN LEN(d.Digits) = 11 AND LEFT(d.Digits, 2) = '03' THEN LEFT(d.Digits, 4) + '-' + RIGHT(d.Digits, 7) END AS Phone,
           ISNULL(m.City, 'Unknown') AS City,
           COALESCE(TRY_CONVERT(DATE, r.SignupDate, 23),  TRY_CONVERT(DATE, r.SignupDate, 103),
                    TRY_CONVERT(DATE, r.SignupDate, 105), TRY_CONVERT(DATE, r.SignupDate, 106)) AS SignupDate,
           TRY_CAST(TRIM(REPLACE(REPLACE(r.FirstOrderAmount, ',', ''), 'Rs', '')) AS DECIMAL(10, 2)) AS FirstOrderAmount
    FROM stg.WebSignupRaw r
    CROSS APPLY (SELECT LTRIM(RTRIM(REPLACE(r.FullName, '  ', ' '))) AS n) t
    CROSS APPLY (SELECT LEFT(t.n, CHARINDEX(' ', t.n + ' ') - 1) AS First, LTRIM(SUBSTRING(t.n, CHARINDEX(' ', t.n + ' ') + 1, 50)) AS Last) f
    CROSS APPLY (SELECT REPLACE(REPLACE(REPLACE(r.Phone, '+', ''), '-', ''), ' ', '') AS s) x
    CROSS APPLY (SELECT CASE WHEN LEFT(x.s, 2) = '92' AND LEN(x.s) = 12 THEN '0' + SUBSTRING(x.s, 3, 10) ELSE x.s END AS Digits) d
    LEFT JOIN etl.CityMap m ON m.Variant = LOWER(TRIM(r.City))
), Checked AS (
    SELECT *, CASE WHEN Email = '' THEN 'Blank email'
                   WHEN Email LIKE '% %' OR Email NOT LIKE '_%@_%._%' THEN 'Invalid email'
                   WHEN Phone IS NULL THEN 'Invalid phone' END AS RejectReason
    FROM Cleaned
), Ranked AS (
    SELECT *, ROW_NUMBER() OVER (PARTITION BY Email ORDER BY SignupDate DESC, SignupID DESC) AS rn
    FROM Checked WHERE RejectReason IS NULL
)
SELECT SignupID, FullName, Email, Phone, City, SignupDate, FirstOrderAmount
INTO stg.WebSignupClean FROM Ranked WHERE rn = 1;
SELECT * FROM stg.WebSignupClean ORDER BY SignupID;

What this query does

The same CTEs, then ROW_NUMBER (Day 8) numbers the valid rows within each email address, newest sign-up first. Only number 1 is kept. Ayesha signed up twice ('Ayesha.Khan@Gmail.com ' on 2 November and 'ayesha.khan@gmail.com' on 5 November); her 5 November row (ID 6) is kept. Bilal's 7 November row (ID 11) beats his 2 November row. The raw emails were different strings, so de-duplicating before cleaning would have kept both. The result is 7 clean rows with proper names, one phone format, real cities, real dates and real numbers.

📍 De-duplicate on the cleaned value: "Ayesha.Khan@Gmail.com " and "ayesha.khan@gmail.com" are one person.

#18

18. Account for every raw row

SELECT (SELECT COUNT(*) FROM stg.WebSignupRaw)    AS RawRows,
       (SELECT COUNT(*) FROM stg.WebSignupClean)  AS CleanRows,
       (SELECT COUNT(*) FROM stg.WebSignupReject) AS RejectedRows,
       (SELECT COUNT(*) FROM stg.WebSignupRaw) - (SELECT COUNT(*) FROM stg.WebSignupClean)
         - (SELECT COUNT(*) FROM stg.WebSignupReject) AS DuplicatesRemoved;

What this query does

12 raw rows = 7 clean + 3 rejected + 2 duplicates removed. Every row is accounted for. This one line is the transform's equivalent of Day 22's reconciliation: if the three numbers on the right ever stop adding up to the one on the left, a rule has lost or duplicated rows.

📍 Raw = clean + rejected + duplicates. If it does not add up, a row went missing.

#19

19. What still needs a person: NULLs left by the rules

SELECT SignupID, FullName, City, SignupDate, FirstOrderAmount,
       CONCAT_WS(', ', CASE WHEN City = 'Unknown' THEN 'city not recognised' END,
                       CASE WHEN SignupDate IS NULL THEN 'date not recognised' END,
                       CASE WHEN FirstOrderAmount IS NULL THEN 'amount missing or not a number' END) AS Warnings
FROM stg.WebSignupClean
WHERE City = 'Unknown' OR SignupDate IS NULL OR FirstOrderAmount IS NULL;

What this query does

One clean row is usable but not perfect: Zain Ali (ID 7) has a valid email and phone, but his city was the text 'NULL', his date '2026-13-45' is impossible and his amount was 'abc'. Rejecting him would lose a real customer, so he is kept, and this query lists what is still wrong in plain words. CONCAT_WS joins only the warnings that apply, separated by commas, and skips the NULLs.

📍 Some rows are usable but imperfect: keep them, and list what is still wrong.

Self-test: answers

CONVERT or TRY_CONVERT in a load? TRY_CONVERT, then check for the NULLs it leaves. CONVERT stops the whole statement at the first bad value (step 9); TRY_CONVERT lets the good rows through and makes the bad ones countable.

Why de-duplicate after cleaning, not before? Duplicates rarely match exactly. "Ayesha.Khan@Gmail.com " and "ayesha.khan@gmail.com" are different strings and the same person; only the cleaned values show it.

Reject, or keep with a warning? Reject a row when the warehouse cannot use it or could misuse it: no valid email or phone means no way to identify or contact the person. Keep it with a warning when it is still a real, usable customer and only a detail is missing (Zain Ali: unknown city, unreadable date and amount).

Why views for the AdventureWorks rules? A view stores the rule, not a copy of the data, so it always reflects the latest extract, can be read and tested on its own (step 3), and the load on Day 24 becomes a simple INSERT ... SELECT from the view.

Why is "02/11/2026" 2 November here? Because the rule says day-first (styles 103 and 105), which is the convention of the source (a Pakistani website). The same text from a US system would mean 11 February. A transform rule for dates is a decision about the source, and must be written down.
